未接线模块清单（2026-11-08 扫描）

扫描 include/*.h 与 src/*.cpp 的引用关系，找出「有实现但固件不用」的模块。 目的不是删代码，而是让「有实现」和「有接线」在文档上分得开。

分类

A. 完全零引用（连测试都没有）

模块 规模 状态
include/IncrementalPID.h 144 行 增量式 PID 备选实现，从未接入固件，也无测试

这是唯一一个「写了但没有任何地方用」的模块。保留原因：可能是为将来 切换 PID 形式预留的。若确认不再需要应删除——死代码会让人误以为 有两条实现路径可选。

B. 有实现、有测试，但固件不调用

模块 引用处 影响
include/AdaptiveGainDamper.h 仅 test_host/test_adaptive_gain_damper.cpp 自适应增益阻尼器未接入
include/AdrcController.h 仅 test_host/test_adrc_controller.cpp ADRC 控制器未接入
include/GenericControlAllocation.h 仅 test_host/test_generic_allocation.cpp 通用分配器未接入（当前用机型专属分配器）
include/LiquidRocketAllocator.h 仅 test_host/test_liquid_rocket_allocator.cpp 液体火箭分配器：机型未烧过，代码已就绪
include/NavAidLossDetector.h 仅 test_host/test_nav_aid_loss.cpp 导航辅助丢失检测器未接入（见 CTL-005 §5）

这一类的共同特征：单测通过、run_all.sh 里跑、但固件从不实例化。 从「测试全绿」看不出来，从「代码存在」也看不出来。

C. 经 src/state_data.h 间接使用（实际在用）

模块 引用链
include/IMU_AutoCalibrator.h state_data.h → 各传感器任务
include/MedianFilter.h state_data.h → 滤波链

这两个不是未接线，只是没被 .cpp 直接 include。扫描时容易误判， 判据应是「能否追到固件的调用链」，不是「有没有 .cpp 直接 include」。

判据

排查「某模块是否真的在用」时：

  1. grep -rl "模块名.h" --include=*.cpp src/ —— 零结果不代表没用
  2. 再查 --include=*.h src/ include/ —— 可能被其它头间接包含
  3. 最后追调用链：从 main.cpp / flight_control.cpp 往下找实例化点

只看第 1 步会把 IMU_AutoCalibrator 和 MedianFilter 误判成死代码。

  • IncrementalPID.h 的去留需要决策：删除，或在文件头标注「备选实现，未接入」
  • B 类五个模块各自要不要接线，需要按机型需求逐个判断

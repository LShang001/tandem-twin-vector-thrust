## 0. 一句话结论

控制与导航内核的结构是这套代码最扎实的部分——分配层纯函数化、参数唯一事实源、安全关键默认值有编译期断言。
问题集中在三个方向：

1. **固件内部逻辑缺陷**：MAVLink 门控自我阻断、参数写入不拦非法值、健康计数漏掉主丢帧路径；
2. **观测判据的有效性**：`ring_drop=0`、`health` 全绿这两条正在被使用，但已不能证明数据完整；
3. **注释与实现漂移**：共轴参数段同时存在三套数值口径，下一批改动的人会按错的量级调参。

P0 三项（FIX-01/02/03）属于"平时不出事、出事查不到"，优先于任何新功能。

### 1.1 硬约束：上位机协议冻结（2026-11-13 用户确认）

**AnoCom、MAVLink、Serial5 制导帧、DETA100、CAN 帧的格式、字段、频率、帧集全部已定稿，
固件不得单方面变更。** 由此推出三条排期规则：

- **不加字段**：诊断量想新增时，先复用现有字段（如把 IMU 丢弃计数并入 `ring_drop`），
  或走 AnoVars 0xF2（变量通道，不改帧结构）与 DBG 文本命令；不得扩 0xF4/0xF5 载荷。
- **不改频率**：注释与实现不符时改注释，不改实发频率。
- **不放宽/收紧取值语义**：参数写入只拦「非法值」（NaN/Inf/量级明显越界），不做业务包线——
  业务包线由上位机与 `params.py` 定义，固件单方面收紧会让现有调参流程出现失败回包。

需要动协议才能根治的问题（如 AnoCom 与 Serial5 无 CRC），**在本仓只登记风险、做接收端兜底**，
根治属于跨系统变更，须与上位机同版本协商，不在本计划内。

### 3.2 P0 条目详情

#### FIX-01 MAVLink 双重间隔门控

- **位置**：`mavlink_bridge.cpp:116-121`（`mavSend` 内再次调用）；外层见 `communication.cpp:2340/2357/2376/2426/2452/2471/2491/2533/2557`
- **现象**：地面站用 `SET_MESSAGE_INTERVAL` 设置过任意可调消息后，该消息永久停发，无日志。
- **机理**：`mavIntervalOk(id)` 语义是「判断 + 到点则写 `last_us`」。外层调用通过并写入当前时刻，`mavSend` 内立刻用同一 id 再判，`now - last_us` 只有几微秒，必然小于间隔 → 返回 false。未设置间隔（`iv==0`）时两次都直接返回 true，所以默认路径看不出来。
- **修法**：拆成两个函数——`mavIntervalDue(id)`（只读判断）与 `mavIntervalMark(id)`（到点写入）；`mavSend` 只做 `mavIntervalDue`，写入由真正发出去之后执行。或退一步：`mavSend` 内删掉该判断，间隔语义完全由外层承担。**不改消息集、不改默认分频、不改帧格式**——修完的行为是「恢复 SET_MESSAGE_INTERVAL 的协议约定」，不是新协议。
- **验证**：宿主新增用例，模拟 `SET_MESSAGE_INTERVAL` 后统计 1 s 内 tx 帧数应 >0；上板用 QGC 设 ATTITUDE 10 Hz，观察 `proto` 统计的 tx 帧数。回归确认未设间隔时各消息分频与修前逐帧一致。
- **风险**：低（仅 MAVLink 分支）。**红线**：否。

#### FIX-02 参数写入只拦非法值

- **位置**：`ano_params.cpp:212-241`（`anoParamDeserialize`）、`:452-453`（写入后 `applyFlightCtrlParams()`）
- **现象**：NaN/Inf 已被挡（现有 `isfinite`），但「有限但量级错乱」的值（如 `rate_roll.kp=1e6`）能直接进控制环并下一拍生效。
- **机理**：反序列化只查长度、类型、`isfinite`；`applyFlightCtrlParams()` 只做量纲换算与同步。
- **修法**（协议冻结口径）：**不做业务包线**，只拦明显非法值——整张表统一按「绝对值上限 = 该字段出厂默认值的 100 倍，且不超过 1e6」判定，超出拒绝并回 0x00 校验帧。业务包线仍由 `GCS/server/params.py` 与上位机负责，固件不重复定义，避免两套规则打架、避免打断现有调参流程。
- **验证**：宿主用例写入 1e7 / NaN / Inf 均被拒且参数不变；写入 `2× 默认值` 必须**通过**（证明没有误收紧）；`param dump` → `param load` 全量快照仍 169/169 通过。
- **风险**：低。**红线**：否。

#### FIX-03 丢帧不计数导致健康判据失真

- **位置**：`sensor_imu.cpp:431-443`（backlog 超 16 时 pop 到剩 8，不计数）、`ImuSampleRing.h:40-44`（只有 push 满才 `drop_count_++`）
- **现象**：`health` 显示 `ring_drop=0`，但控制可能一直在用旧数据——这正是 2026-11-10 延迟事故的同类假绿。
- **修法**（协议冻结口径）：把 backlog 主动丢弃的帧数**累加进现有 `drop_count_`**（`imuRingDropCount()` 已经通过 0xF4 的既有字段上报），**不新增帧字段、不扩载荷**。语义改为「IMU 帧丢弃总数（含积压裁剪）」，并同步更新 `health` 文案、`tools/verify_board.py` 判据与 `AGENTS.md` 里「ring_drop=0」的表述。
- **验证**：人为制造积压（DBG 长输出）观察 `ring_drop` 增长；正常飞行必须为 0。
- **风险**：低（只加观测）。**红线**：否。

## 5. 明确不做 / 暂缓（附理由）

| 项 | 决定 | 理由 |
|---|---|---|
| 给 AnoCom / Serial5 加 CRC、改帧结构 | **不做** | 上位机协议已定稿，固件单方面改帧会让现有 GCS 与制导机全部失联；根治属跨系统变更 |
| 扩 0xF4/0xF5 载荷加诊断字段 | **不做** | 灵活格式帧的载荷长度是上位机解析约定的一部分；诊断量复用现有字段或走 0xF2/DBG |
| 删光流整链（`sensor_peripheral.cpp` 约 1400 行） | 不删，只标注「默认不编译」并在 health 显示 `flow:OFF` | 硬件未装但代码已验证过，删了将来重装要从 git 捞；成本是每次读代码多一层判断 |
| `handleNavigationSystem`（约 3000 行）拆分 | 暂缓，单独立项 | 纯重构，收益是可维护性，风险是碰到未覆盖分支；当前无此需求 |
| KF 协方差钳位只钳对角 | 记录，暂不改 | 需要先论证「钳对角是否真的破坏正定性、会不会影响现网」；有 `S_min` 除零兜底，实际风险未量化 |
| 纯惯导参考 9.79 与 EKF WGS84 口径 | 记录，随 `param_align` 启用时一并处理 | 只影响 GNSS 延时估计的参考轨迹（当前宏关闭），量级 0.004 m/s² |
| IMU 冻结检测只在解锁+油门≥3% 生效 | 保留 | 静止时「数据不变」与「数据冻结」不可区分，门控是有意设计；代价是地面预检盲区，归入检查单 |
| `NavAidLossDetector` 接入 | 批次 C 决策 | 要么接入，要么删掉以免误判为在役；倾向接入（已有宿主测试） |

# VER-010 实机烧录与上电验证记录（2026-11-07）

> 证据等级：**L4 实机**（真实硬件 + 真实固件 + 真实传感器）。不是仿真。
> 目的：确认「当前代码编出的固件」能烧进去、能起来、传感器与参数与代码一致。

---

## 1 硬件与环境

| 项 | 事实 |
|---|---|
| 主机 | 荣耀 MagicBook X14P（`MagicBook-X14P`，经 SSH 远程操作） |
| 飞控板 | WeAct MiniSTM32H743VIT6，STM32H74x/75x，flash 2048 KB，bank0 base `0x08000000` |
| 调试器 | CMSIS-DAP v2（`VID_0D28&PID_0204`），OpenOCD 识别为 SWD，DPIDR `0x6ba02477` |
| 调试串口 | 未使用（见 §5 的边界说明） |
| 数传 | Silicon Labs CP210x（COM6），AnoCom 协议遥测 |
| 烧录速率 | `adapter speed 100`（100 kHz，按 AGENTS.md 要求降到 20–100 kHz 区间） |

## 2 烧录结果

命令（OpenOCD 直烧，不经 PlatformIO）：

```
openocd -f interface/cmsis-dap.cfg -f target/stm32h7x.cfg \
  -c "adapter speed 100" \
  -c "program firmware.bin 0x08000000 verify reset exit"
```

输出关键行：`Programming Finished` → **`Verified OK`** → `Resetting Target`。

固件来源：`SingleEdf4Vane` 环境编译的 `firmware.bin`，396144 字节，
与本机 `.pio/build/SingleEdf4Vane/firmware.bin` 逐字节一致（传输后核对大小）。

## 3 上电验证

### 3.1 固件版本与机型

| 检查 | 结果 | 判据 |
|---|---|---|
| 参数表在位 | **169 项** | 与 `ANO_PARAMS_COUNT=169` 一致；旧固件是 133 或 164 |
| 机型 | **`veh=SingleEdf4Vane`** | `health` 直接给出 |
| 单涵道分支参数 | `sedf.ctrl_vane_deg=20.0°`、`rate_roll.kp=57.3` | 与 `FlightCtrlParams.h` 的 `ctl_vane_deg=20.0f` 及 57.3 s⁻¹ 换算注释一致 |

**判据说明**：`Verified OK` 只证明字节写进了 Flash，不证明固件是新的。
真正的证据是**读回 169 参数**——只有当前代码才编出这个数量。

### 3.2 传感器与实时性

| 项 | 读数 | 判据 |
|---|---|---|
| IMU 真实采样率 | **2000.4 Hz**（256 样本，min 1856 / max 2162） | 设计 2000 Hz，用 `0xF2` 变量帧 `imu_rate` 读取（**非 DBG 路径**） |
| IMU 校准 | `cal=1` | 已校准 |
| IMU 掉帧 | `drop=0.00s` | 无 |
| SPSC ring | `ring_drop=0`、`isr_empty=0` | P1 架构无丢包 |
| IMU 原始读数（静止） | `ax=+0.0952`、`ay=+0.9956`、`az=+0.0034` | 重力集中在 y 轴（板子平放），读数稳定；单位 g |
| IMU 温度 | `29.71 °C` | 稳定（min=max，无跳变） |
| 姿态 | `R=-5.36° P=-0.09° H=352.87°`（EKF） | 静止稳定 |
| 气压 | `1016.61 hPa`、`31.49 °C`、`alt=-2.36～-3.57 m` | 室内读数合理 |
| **磁力计** | **`mag_on=0`、`mag_cal=0`、`mag_seq=0`、`mag_age=UINT32_MAX`** | **未检测到磁力计硬件**（见 §5） |
| GNSS | `fix=0 sv=0` | 室内无信号，`fake_origin=1` 为预期降级 |
| CPU | `49.4%` | 200 Hz 调度下正常 |

### 3.3 链路

遥测帧率 982 帧/s，坏帧 0；参数命令 `0x01/0x02/0x03` 各 5/5 成功，写确认 5/5。

### 3.4 IMU 轴映射实机验证

板子静止平放时，`0xF2` 变量读到的**芯片原始轴序（RUB）**加速度：

```
raw(RUB) = (+0.0952, +0.9956, +0.0034) g
```

按固件转换律 `bX=-sZ / bY=+sX / bZ=-sY`（AGENTS.md §IMU 轴映射）换算：

```
FRD = (-0.0034, +0.0952, -0.9956) g
|FRD| = 1.0001 g   （相对 1 g 误差 0.015%）
```

三条结论：

1. **重力几乎全部落在 `bZ` 且为负**——符合「FRD 系 `z_b` 指地、静止时加速度计测到 −1 g 比力」，
   说明轴映射（含两处符号反转）在实机上成立。
2. **模长 1.0001 g**，相对误差 0.015%，静止无明显振动或标定偏差。
3. 与 EKF 姿态 `R=-5.36° / P=-0.09°` 自洽：机头朝天时 `roll/pitch≈0` 正是本项目
   「悬停姿态判据」（MOD-002 §0 与 AGENTS.md §当前约定 都要求如此）。

> 意义：这是 `MOD-002 §0`（坐标系唯一正本）与 `AGENTS.md §IMU 轴映射`
> 在**真实硬件**上的直接验证，而不只是纸面约定或仿真假设。

### 3.5 陀螺零偏与噪声（静止）

`0xF2` 读三轴**原始**角速度（芯片轴序），取 5 秒窗口：

| 轴 | 均值 [dps] | 最小 | 最大 | 峰峰值 |
|---|---|---|---|---|
| gx | −0.0398 | −0.1619 | +0.1433 | 0.305 |
| gy | −0.0392 | −0.1003 | +0.0828 | 0.183 |
| gz | −0.0295 | −0.1516 | +0.0926 | 0.244 |

判读：

- 三轴零偏都在 **±0.04 dps** 以内。ICM-42688-P 手册的零偏典型量级是 ±0.5 dps，
  这里小一个数量级——**板子静止、无振动、校准有效**。
- 峰峰噪声 < 0.31 dps，对应 `health` 里的 `gz_bias_dps=-0.028`（固件静基座估计值），
  与原始读数同量级，互相印证。
- 这一项与 §3.4 的加速度计验证合起来，说明 IMU 通道**从原始读数到姿态都是健康的**。
  唯一缺的是磁力计（§5 所述）。

### 3.6 在线调参链路（0xE1 写入）验证

选最安全的参数 `sedf.yaw_trim_deg`（静止未解锁时不生效）做完整链路验证：

| 步骤 | 写前读回 | 写后读回 | 结果 |
|---|---|---|---|
| 写 0.5 | 0.0 | 0.5 | ✓ 生效 |
| 写回 0.0（DBG 模式下） | 0.5 | 0.5 | ✗ 被拒，提示「固件处于 DBG 模式（参数链路暂停）」 |
| `dbg off` 后再写 0.0 | 0.0 | 0.0 | ✓ 生效 |

最终确认：`sedf.yaw_trim_deg=0.0`、`rate_roll.kp=57.3`（控制参数未被误改）。

> ★ **操作约束（实测）**：DBG 模式下参数链路暂停。用 `vars watch` / `dbg` 命令之后，
> 紧接着写参数会被拒。正确顺序是先 `cli.py dbg off` 再写参数；GCS 的报错信息
> 已经直接给出这个指引。
>
> 另一个观察：第二次「写回 0.0」虽然报「未生效」，但 `dbg off` 后读回已经是 0.0
> ——说明那次写入实际生效了，只是确认帧被 DBG 模式吞掉。这与 `cli.py` 里
> 「写入实际生效但确认帧没抓到」的注释一致。**判读「写失败」时不能只看确认帧，
> 要退出 DBG 后重读一次实际值。**

## 4 一个必须记住的口径坑

`tasks` 命令里 ICM42688 任务显示 **实际 1284 Hz**（名义 2000）、丢执行 50 万次。
**这不是固件缺陷**：`tasks`/`health` 走 DBG，打印本身会显著加剧丢拍
（AGENTS.md §调度统计口径 已写明）。

用**非 DBG** 的 `0xF2` 变量 `imu_rate` 实测才是 2000.4 Hz。

> 判据：任何「IMU 速率不达标」的结论，必须先排除测量路径本身的副作用。
> 用 DBG 打印出来的频率不能作为速率证据。

## 5 边界与未验证项

- **未做电机驱动测试**：全程 `unlock=0`、`RC3=0`，没有解锁、没有给油。
- **没有飞行**：只验证烧录、启动、传感器读数、参数表。
- **磁力计未检测到**：`mag_on = magSensor.isPresent() = false`、`mag_cal=0`、
  `mag_seq=0`、`mag_age=UINT32_MAX`。`mag_refok=1` 只表示参考场表可用，
  不表示有磁数据。**这不是软件判据的错，是硬件层没有检测到磁力计**——
  要么本机未装/未接，要么驱动初始化失败。当前航向没有绝对参考
  （EKF 以 `fake_origin=1` 降级运行）。下次接磁力计后需重新验证 `mag_on=1` 与 `mag_cal=1`。

  **证据链（本轮补）**：DBG `magcal` 输出
  `chip=NONE collecting=NO samples=0 cal=NONE`，
  `nav: present=0 ref=1 age=4294967295ms norm=0.0uT ndev=49.0 hdg=0.0deg dip=0.0deg ... reason=stale`。

  判据来源：`MagSensor::isPresent()` 返回 `_chip != MagChip::NONE`，
  而 `_chip` 只在 `_ist.begin(wire)`（IST8310，I2C 0x0E）或
  `_qmc.begin(wire)`（QMC5883L，0x0D）成功时才被赋值。
  两者都失败 → `_chip` 保持 `NONE`。**即 I2C 总线上没有这两个地址的芯片响应**。

  > 一个易误读项：`ndev=49.0` 看着像「航向偏差 49°」，实际是
  > `mag_status.norm_dev_ut`（磁感应强度偏差，单位 uT）。`norm=0.0` 时
  > 它等于参考场强本身（约 49 uT），是「没数据」的表现，不是航向错误。

  **软件侧排查结论（逐项排除，均正常）**：
  1. 初始化顺序正确——`sensor_imu.cpp:68-69` 先 `Wire1.begin()` + `setClock(400000)`，
     第 74 行才 `magSensor.begin(&Wire1)`；不存在「总线未就绪就探测」的问题。
  2. 引脚无冲突——`state_data.h:316-317` 定义 SDA=PB7 / SCL=PB6；
     单涵道的执行器是 PA0–PA3（四舵）、PC8（推进）、PE6（使能），不重叠。
  3. 探测逻辑本身正确——先试 IST8310（0x0E）再试 QMC5883L（0x0D），
     两地址不同可共存，失败才落 NONE。

  因此**软件侧没有可修的缺陷**，问题在硬件（未装/未接）或总线物理层。

  **另一个影响排查效率的事实**：初始化失败时的日志（`[Error] Magnetometer Not Found!`
  与「请检查 SDA/SCL 与供电」）走 `Serial8`，即板子的 USB CDC。
  本次实验机上的 USB 设备列表里**没有 STM32 的 USB 设备**（只有 DAPLink 与 CP210x），
  说明**板子的 USB 口没插**，所以看不到这份启动日志。
  下次排查磁力计应先接上板子 USB（届时会多出一个 COM 口），
  直接看 `[Init]/[Error]` 行即可判定。
- **调试串口未打通**：DAPLink 的 CDC（COM10）在 921600/460800/230400/115200/57600
  五档波特率下**全部 0 字节**，判断该 CDC 未桥接到目标板 UART
  （DAPLink 固件的 CDC-UART 桥接未启用，或板子 UART TX 未接到调试器 RX）。
  COM6（CP210x）是 AnoCom 遥测流，不是 DBG 控制台。
  本轮所有 DBG 命令均经 AnoCom 的 DBG 模式通道走通，不影响结论，
  但独立调试串口链路仍未验证。
- **烧前未读到板上原固件**：因上一条，无法在烧录前确认原来是什么机型；
  烧后靠 169 参数 + `veh=` + 20°/57.3 反推确认。

## 5.5 长时运行后的 CPU 统计失真（已定位原因，未改代码）

板子连续运行 93 分钟后再读 health：

```
veh=SingleEdf4Vane mode=0 unlock=0 uptime_s=5604
loop cpu_permille=4090 max_pass_us=3098 win_s=590
```

`cpu_permille=4090` 即 409%——单核不可能超过 100%，数字自相矛盾。
刚烧录时（Round 38）同一项是 `493`（49.3%）。

**根因：两个时间基准用了不同的计时器。**

| 量 | 用的计时器 | 回绕周期 |
|---|---|---|
| `uptime_s` | `millis()` | 49.7 天 |
| `exec_sum_us` 累加 | 每次 `micros()` 差值（u32 减法，短间隔内正确） | — |
| 统计窗口 `window_us` | `micros() - s_stats_window_start_us` | **71.6 分钟** |

板子跑了 5580 秒（93 分钟），`micros()` 已经回绕过一次（4294.97 秒）。
窗口起点在开机时设定，现在 `micros()` 已绕回，无符号减法得到的窗口被算小
（显示 590 秒；按 5580−4295 推算应约 1285 秒，与实测 590 仍有出入，
说明重置时机或回绕次数还要再核）。而 `exec_sum_us` 是 u64 累加、不受回绕影响
——分子没变小、分母变小，比例被放大成 409%。

**复测验证（2026-11-08 00:43，OpenOCD reset run 重启后 37 秒）**：

```
uptime_s=37  cpu_permille=474（47.4%）  win_s=33  max_pass_us=20247
```

CPU 回到 47.4%，与刚烧录时的 49.3% 一致——**确认 409% 是长时运行后的失真，
不是固件在某些工况下真的跑到 400%**。根因假设（micros 回绕）由此得到验证。

同一次读数里 max_pass_us=20247（20.2 ms）与 Round 38 的 20302 一致，
说明这个 20 ms 尖峰是**启动瞬态**（初始化时的一次长执行），不是持续问题：
运行 93 分钟后的读数是 3098（3.1 ms）。

**影响范围**：只影响 `health` 的 CPU 显示与 `tasks` 的负荷列，
不影响控制、导航或任何飞行行为。长航时（超过 71 分钟）后该指标不可信。

**未改代码的原因**：`task_scheduler.cpp` 属调度层，`AGENTS.md` 的安全关键
修改规则要求「任务频率/定时器/调度/控制周期」未经明确要求不改。
这里只记录现象与根因，供后续专门排期。

**短期判据**：CPU 负载只在 `uptime_s < 4000` 时读；超过该值改用
`max_pass_us`（实测 3.1 ms，正常）判断实时性是否健康。

## 5.6 冷启动序列观察（2026-11-08 01:00）

OpenOCD `reset run` 复位后按时间点连续读 `health`，记录启动到稳态的过程：

| 观察点 | uptime | cpu_permille | max_pass_us | win_s | imu Hz | drop | ring_drop | rpy_deg |
|---|---|---|---|---|---|---|---|---|
| t=5 s | 68 s | 484（48.4%） | 20249 | 64 | 2132.2 | 0.00 | 0 | −5.35 / −0.26 / 353.17 |
| t=15 s | 81 s | 485（48.5%） | 20249 | 77 | 1999.6 | 0.00 | 0 | −5.36 / −0.25 / 353.16 |
| t=60 s | 132 s | 489（48.9%） | 20249 | 128 | 1968.9 | 0.00 | 0 | −5.35 / −0.26 / 353.09 |
| t=120 s | 195 s | 491（49.1%） | 20249 | 191 | 1999.6 | 0.00 | 0 | −5.35 / −0.21 / 353.01 |

（t=30 s 那次 CLI 读数失败，无数据，不影响结论。）

三条判读：

1. **CPU 从 48.4% 缓慢爬到 49.1%**，全程稳定在 50% 以下，没有启动冲击。
2. **`max_pass_us` 恒为 20249**——从 t=5 s 起就没再变过。这确认了那个 20 ms
   尖峰是**开机初始化的一次长执行**，此后从未复现（运行 93 分钟后是 3098 us）。
3. **IMU 速率在 1968–2132 Hz 间波动**（5 秒窗口瞬时值），均值贴合 2000 Hz；
   `drop=0`、`ring_drop=0` 全程无丢帧。姿态从第一秒起就稳定在 −5.35° 附近，
   无收敛过程——因为静止且无扰动，EKF 一开始就在正确点上。

> `conv=0` 是预期结果：室内无 GNSS、`fake_origin=1`、且本机磁力计未检测到
> （见 §5），EKF 没有绝对参考可收敛。这不代表 EKF 异常。

## 6 复现步骤
```bash
# 1) 编译（本机）
cd TandemVec_FCS && pio run -e SingleEdf4Vane

# 2) 传固件到目标机
scp .pio/build/SingleEdf4Vane/firmware.bin magicbook:D:/.../tmp_fw.bin

# 3) 烧录（目标机，OpenOCD 直烧）
openocd -f interface/cmsis-dap.cfg -f target/stm32h7x.cfg \
  -c "adapter speed 100" \
  -c "program D:/.../tmp_fw.bin 0x08000000 verify reset exit"

# 4) 验证（目标机，GCS CLI）
cd TandemVec_FCS/GCS
py -3.13 -X utf8 server/cli.py --port COM6 device        # → 169 参数
py -3.13 -X utf8 server/cli.py --port COM6 dbg health     # → veh / IMU / EKF
py -3.13 -X utf8 server/cli.py --port COM6 vars watch imu_rate -t 6   # → 2000 Hz
```

**sweep 的 3 个失败**（判据 `max_roll/pitch ≤ 30°`）：

| 用例 | 参数 | 实测 | 判据 |
|---|---|---|---|
| `lever_low` | L=0.08 m | max_pitch **46.8°** | >30° |

| `combined_low` | m=0.70 / T=12 / L=0.08 / Iy=0.03 | max_roll **45.4°**、max_pitch **36.5°** | >30° |

**这些是已知的鲁棒性边界，不是新缺陷**。summary.md 原文：

> 套件退出码：1（0=全部通过；1=任一阶段失败。注意：**历史基线 MC/sweep 未达 100%，
> 默认运行即返回 1，是真实门禁。**）

共轴对「力臂变小 / 俯仰惯量变大」敏感，与 VER-007 的摄动结论一致（惯量×1.1 → 5/5 FAIL，
max_pitch 25–26°）。力臂 0.15→0.08 会让同一舵角产生的力矩降 47%，
姿态权限不足属物理预期。

**物理原因定量验证**：力臂 L 从 0.15 → 0.08 m，同一舵角产生的力矩降到
53.3%（降 46.7%）；线性模型预测姿态偏差放大 1/0.533 = **1.88 倍**。
实测 max_pitch 从 23.4°（多个 PASS 用例的共同值）升到 46.8°，**放大 2.00 倍**，
与理论相差 6.7%。

这证明 `lever_low` 的 FAIL 不是控制律缺陷，而是**执行器力矩权限不足**——
力臂小了近一半，同样的舵偏角产生的控制力矩也少了近一半，姿态抗扰/跟踪能力
必然下降。要改善只能增大舵面/舵角或加大力臂，属机械设计约束，软件参数补不了。

**`iy_high` 的同类验证**：Iy 从 0.05 → 0.08 kg·m²，同一力矩产生的角加速度
降到 62.5%（降 37.5%）；理论姿态偏差放大 1/0.625 = **1.60 倍**。实测 max_pitch
从 23.4° 升到 37.4°，**放大 1.60 倍**，与理论偏差仅 **0.1%**。

两个用例（`lever_low` 偏差 6.7%、`iy_high` 偏差 0.1%）给出一致结论：
共轴在摄动下的 FAIL 是**惯量 / 力臂的线性效应**，不是控制律缺陷。
控制律在这些配置下的输出仍然正确，只是执行器权限（力矩 / 角加速度）不够。

**关于 `f4=1` 的语义澄清**：`lever_low` 与 `combined_low` 的 `f4` 都是 1，
但两者**没有注入任何故障**（`extra=[]`、`append=[]`）。

F4 的判据是「|姿态误差| > 25° 且 |摆角指令| ≥ 90% dMax 持续 0.5 s」
（`flight_control.cpp:3065`）。当力矩权限不足时，摆角必然打满、姿态必然超限
——这两个条件同时成立，F4 就触发。

所以 **`f4=1` 不等于「真的舵机卡死」**，而是「姿态超限 + 执行器饱和」这个
组合条件成立。它是**启发式**，无法区分：

- 舵机卡死导致超限（真故障）
- 力矩不足导致超限（本轮的摄动场景）

判读时不能只看 `f4` 标志，要结合是否真的注入了 fault。

> 这不是缺陷——判据是明确设计并写在注释里的。但它提醒：「检测到故障」和
> 「真的有故障」是两件事，在摄动场景下会混淆。

**需要区分三类结果**：

| 标记 | 含义 |
|---|---|
| `[PASS]` | 姿态/高度/位置都在判据内 |
| `[DETECTED]` | 故障被检测到（`both_loss_60`/`servo_jam`），**设计预期**，不是失败 |
| `[FAIL]` | 真实姿态超限（上面 3 例），是鲁棒性边界证据 |

套件退出码 1 属设计如此——它不粉饰基线，也不把 `[DETECTED]` 混进失败数。

## 2.3 共轴 roll/pitch 不对称：一个尚未解释的现象（2026-11-08）

MC 100 的统计里，`roll_p50 = 1.26°` 而 `pitch_p50 = 29.3°`，差 23 倍。
逐项排查了可能的不对称来源，**都不是原因**：

| 检查项 | 结论 |
|---|---|
| 执行器映射 | `Mx = l·T·sin(δ_roll)`、`My = l·T·sin(δ_pitch)`，**完全对称**（`CoaxialAllocator.h:13`） |
| 速率环增益 | `BFS_RATE_ROLL_DEFAULT` 与 `BFS_RATE_PITCH_DEFAULT` **逐位相同**（16.042818 / 5.729578） |
| 姿态环增益 | `BFS_ATT_ROLL_DEFAULT` 与 `BFS_ATT_PITCH_DEFAULT` **相同**（2.8 / 0） |
| 惯量 | 分配器分别用 `inertia[1]`(Iy) 与 `inertia[2]`(Iz) 逆解，参数里两者可独立配置 |

**所以不对称不来自控制律或分配层**。可能的来源（**未验证**）：

1. plant 的俯仰通道扰动更大（气动/接触模型）
2. 初始条件在 pitch 方向有偏置
3. 俯仰轴与重力方向的耦合（共轴机体竖立，俯仰倾角直接影响推力竖直分量）

> **诚实标注**：这是一个**开放问题**，不是已解决问题。上面三条都是推测，
> 没有一条被数据验证过。把它写下来的目的是：不要让「pitch 偏大」被误认为
> 已经查清——它只是被**定位到了控制层之外**。

## 2.4d 下降段为什么力矩不够：定量闭环（2026-11-08）

共轴的控制力矩是 `M = l · T · sin(δ)`——**力矩与推力成正比**。
油门收小 → 推力变小 → 同样舵角产生的力矩同比变小。

以 mass=0.84 kg（悬停需 8.2 N）、l=0.15 m、max_thrust=14 N 计算：

| 油门 | 推力 | 最大力矩 | 相对悬停 |
|---|---|---|---|
| 100% | 14.0 N | 2.10 N·m | 170% |
| 70% | 9.8 N | 1.47 N·m | 119% |
| 50% | 7.0 N | 1.05 N·m | 85% |
| **30%** | **4.2 N** | **0.63 N·m** | **51%** |

**下降段油门约 30% 时，控制力矩只剩悬停的一半** → 姿态抗扰能力减半 →
同样的扰动会造成约 2 倍的姿态偏差。这与实测完全吻合：

- `lever_low`（力臂减半）：力矩 53.3% → 姿态偏差**实测放大 2.00 倍**
- 下降段（油门 30%）：力矩 51% → **理论放大约 2 倍**

**两条独立路径（改力臂 / 改油门）得到同一个比例关系**，说明这就是
`M = l·T·sin(δ)` 的直接后果，不是控制器的问题。

**TVC 最低推力 0.35 N 不是限制**：那对应油门 2.5%，远低于下降段实际油门。

**可行的改进方向**（未实施，仅记录）：

1. **下降段保留更高油门**：用更大倾角换下降速度，而不是收油门——
   保持控制力矩。代价是下降轨迹更斜。
2. **下降段限幅姿态指令**：主动降低姿态变化率需求，与可用力矩匹配。
3. **接受现状**：如果实机下降段姿态偏差在安全范围内（无 GNSS 时靠目视），
   则这是物理边界，不是缺陷。

> ★ 不建议做的：**在下降段加大控制增益**。力矩权限不足时加大增益只会让
> 积分饱和更快、超调更大——`lever_low` 的定量验证已经证明偏差主要来自
> 力矩不足，不是环路增益低。

## 2.6 F4（舵机卡死）检测的门限盲区（2026-11-08）

**现象**：`--fault 4`（上摆卡死 +8°）注入后，t=9~12 期间 `f4` 始终为 0，
直到 t=13 数值失效（见 `fw_sil/README.md` 的逐拍表）。

**原因**：F4 判据是「|姿态误差| > 25° 且 **|摆角指令| ≥ 90% dMax** 持续 0.5 s」
（`flight_control.cpp:3065`）。实测卡死后的舵机输出：

| 时刻 | 前摆 | 尾摆 | 对应摆角占比 |
|---|---|---|---|
| t=9 | 72.2% | 31.6% | 44.4% / 36.8% |
| t=12 | 72.2% | 27.8% | 44.4% / 44.4% |

**摆角指令只到 44.4% dMax，离 90% 门限差一倍**，所以判据永远不成立。

**为什么不打满**：卡死的是**一个舵**（上摆，滚转主控），另一个舵仍在工作。
控制律不需要把一个轴打到满舵就能产生部分修正力矩——但**部分修正不足以
抵消卡死**，姿态于是持续翻滚。这就是「指令不到满舵、姿态已经失控」的组合。

**这暴露了判据的设计假设与实际场景不匹配**：90% dMax 门限隐含假设
「卡死后控制器会死命打舵」，而单舵卡死时控制器只会适度补偿另一个舵。

**改进方向**（未实施，需单独评审）：

1. **改用「指令 vs 实际位置」的偏差判据**：卡死通道的实际位置不跟随指令，
   这是最直接、最无歧义的判据（`|cmd - actual| > 阈值` 持续 N 拍）。
2. **降低 dMax 门限**：比如 50%，但会引入「大机动时误报」的风险。
3. **组合判据**：姿态误差大 + 某一通道指令长期不变（卡死的特征）。

**判据的适用边界（理论推理，未实测）**：

| 场景 | 实测摆角 | 控制律行为 | F4 预测 |
|---|---|---|---|
| A. 卡死在满舵位（±dMax） | 已满舵 | 反向打满试图纠正 → 指令 ≥90% | ✓ 会触发 |
| B. 卡在小偏置（+8°，本轮） | 44.4% dMax | 适度补偿 → 指令 44.4% | ✗ 不触发 |

差异的根源：场景 A 里「卡死的位置」本身就是满舵，控制律为了抵消它会
把指令打到反向满舵；场景 B 里卡死位置只有 44%，控制律也就不必打满。

> ★ **这是推理不是实测**。要确认场景 A 真能触发，需要构造「卡死在 ±dMax」
> 的注入并观察 `f4` 是否置位。当前 `--fault 4` 硬编码 +8°，
> `--coax-servojam` 锁存当时位置（可能落在任何位置），都不便于精确构造。
> 在补齐这个实验之前，**不应断言「F4 对满舵卡死有效」**。

> ★ 不建议轻率改这条判据：它对**卡死在满舵位**的场景有效（例如卡在 ±dMax），
> 只是对「卡在小偏置」（+8°）无效。改之前应先明确要覆盖哪类卡死。
> 另外这条判据走的是实飞路径，改动必须重新跑宿主回归与 SIL 验收。

## 2.7 F4 为什么永远不触发：结构性原因（2026-11-08，读码确认）

Round 116 用 `--fault4-deg 15` 把舵机卡在满舵位实测，`f4` 仍为 0。
本轮读代码确认这是**结构性缺陷**，不是参数没调好。

**判定条件**（`ActuatorFaultMonitor::update()`）：

```
roll_bad = |roll_err_deg| > servo_err_deg && |df_cmd_frac| >= servo_cmd_frac
servo_cmd_frac 默认 0.90
```

**`df_cmd_frac` 的来源**（`flight_control.cpp:3096`）：

```
dmax_deg = kDefaultTandemVecParams.dMax * 57.2957795f
df_frac  = gnc_tel.delta_f_deg / dmax_deg
```

**关键**：`delta_f_deg` 是**固件算出的摆角指令**，不是 plant 的实际位置。

卡死在 SIL 里是 plant 侧强制 `p.servo_f = 15°`——固件**完全不知道**舵机没跟上，
它继续按姿态误差算指令。于是：

| 条件 | 实际 | 是否满足 |
|---|---|---|
| 姿态误差 > 25° | roll 翻到 114° | ✓ 满足 |
| 指令 ≥ 90% dMax | 实测 44.4% | ✗ **不满足** |

`df_frac` 上不去的原因是控制链本身：速率环输出角加速度 → 分配层转摆角 →
经限幅后，翻滚时摆角只到 44%，**与舵机是否卡死无关**。

**结论**：F4 的「指令饱和」条件在真实卡死场景下可能**永远不满足**——
因为固件的指令本来就不打满，无论舵机正常还是卡死。这是判据的结构性缺陷。

**真正可靠的判据**应是「指令与实际位置的偏差」`|cmd - actual|`。但 SIL 里
plant 的实际位置没有回传给固件；真实硬件若有舵机位置反馈，这条判据才可用。
在没有位置反馈的构型上，F4 只能靠「姿态误差」单条件 + 更长的持续时间窗，
代价是误报率上升。

**严重性评估：F4 目前是「装饰性检测」（2026-11-08）**

查 F4 触发后到底做什么——只有两处消费：

| 位置 | 用途 |
|---|---|
| `ano_vars.cpp:83` | 遥测变量 `afm_desc`（地面能读到一个 bool） |
| `flight_control.cpp:2972` | 控制输出标志位 `0x04` |

**它不执行任何动作**——不切动力、不强制下降、不改控制模式。

所以「永不触发」的实际影响是**「地面看不到 F4 指示」**，而不是
「该保护时没保护」。**对飞行安全无直接影响**。

但这也意味着 F4 目前是**装饰性检测**：

- 对操作者的价值：卡死后地面能知道「是舵机卡死，不是别的原因」——有诊断价值
- 对飞行安全的价值：**0**（它不会救飞机，因为姿态已崩且无位置反馈可控）

要让 F4 有实际价值，需要两步：①修判据（用指令-实际偏差，需位置反馈）；
②让它执行动作（如强制切动力）。**两步都必须单独评审**——尤其第②步，
在姿态已失控时切断动力可能让坠落姿态更不可控。

> ★ 这条不改代码：F4 走实飞路径，改判定逻辑必须重新评估误报风险并跑全量回归。
> 本轮只把机制查清并记录，为后续决策留依据。

## 2.11 三机型质量参数的来源核对（2026-11-08）

查「仿真 plant 的质量与飞机模型是否一致」时发现三个机型各用各的参数，
初看像矛盾，核对后确认是设计：

| 机型 | 质量来源 | 值 |
|---|---|---|

- 纵列：`check-param-parity.py` 对比 `aircraft-model.json` ⇄ `TandemVec_Config.h`

> ★ 初看「SIL plant 的 0.84 与 JSON 的 0.7 不一致」很像是矛盾，实际是
> **拿错了机型对比**——0.84 是共轴的，0.7 是纵列的。这类「跨机型误比」
> 是查参数一致性时最容易犯的错。

## 2.12 「静默跳过」排查（2026-11-08）

Round 135–136 的教训是「静默跳过比报错更危险」。全仓扫 `tools/check-*.py`
的 `continue`，共 6 个文件 36 处，逐个分类：

| 检查器 | continue 数 | 判定 |
|---|---|---|
| `check-doc-stats` | 3 | 正常：①跳过无关目录 ②`[SKIP]` 有打印 ③读文件失败跳过 |
| `check_imu_axis_map` | 2 | 正常：①跳过不匹配行 ②「未找到」记为 problem |
| `check-codeblock-paths` / `check-links` / `check-code-comments` | 9 / 7 / 14 | 抽查均为「跳过不适用文件/行」，非关键比较 |

**结论**：除了已修的 `check_coax_parity`，其余检查器没有「静默跳过关键比较」的问题。

**判据**（给以后加检查器用）：

- `continue` 跳过的是**不适用的对象**（无关目录、不匹配的行）→ 正常
- `continue` 跳过的是**本该检查但抓不到的项** → **必须打印出来**
  （如 `[SKIP]` / `[跳过]` / 记为 problem），否则 PASS 会骗人

> ★ 这条判据来自实际踩坑：`check_coax_parity` 的 `len(vals) < 3: continue`
> 让「某项没抓到」与「某项真的三项一致」在输出上完全一样，Round 134
> 因此把未完成当成了完成。

## 2.5 不同 SIL 入口支持不同参数，且都不校验未知参数

排查三轮后的最终结论：--gain-scale 系列在 SIL 里「完全无效果」的真实原因，
是不同入口支持不同参数、且都不报错地忽略不认识的参数。

| 入口 main | 支持的参数 |
|---|---|
| fw_sil_env_main.cpp（纵列 / 共轴 / real-nav） | --gain-scale / --rate-gain-scale / --att-gain-scale / --fault / --fault-at / --seconds / --real-nav 等 |
| fw_sil_singleedf_main.cpp（单涵道） | **只有 --manual** |

而 build_and_run_singleedf.sh 末尾是 `"$OUT" "$@"`——把参数透传给二进制。
所以传 --gain-scale 2.0 不会报错，只是**被忽略**，跑的还是同一个固定 40 秒场景。
这就是为什么 0.5 / 1.0 / 2.0 / 4.0 四档输出逐字符相同。

★ **这是危险设计**：未知长参数静默忽略。若拿它做 A/B 并据此写结论，
  会得出「参数无影响」的假结论，而实际上参数根本没被读取。
  正确做法是：不认识的长参数直接报错退出。

另有一条与参数无关但同样重要的架构事实：
- 纵列路径（flight_control.cpp:2141）用 const TandemVecParams &P = kDefaultTandemVecParams，
  参数来自 TandemVec_Config.h 的**编译期常量**，不读 kFlightCtrlParams；
- 单涵道路径（mix_and_output_single_edf）读 kFlightCtrlParams（运行时可变）。
所以即使换成支持 --gain-scale 的入口，**对纵列仍然无效**——要改纵列增益只能改
TandemVec_Config.h 重编译。

> 现有结论：--gain-scale 只可能影响走 kFlightCtrlParams 的路径（单涵道/共轴），
> 且必须用支持该参数的入口；纵列 SIL 无论如何都不受影响。
> 未验证：单涵道路径在有激励场景下的增益灵敏度——因为单涵道 SIL 目前
> 只支持 --manual（摇杆直通，mode=0，不走控制律）。

**两个弱覆盖项怎么补**：

- **调度分发**：靠实机 `tasks` 统计（avg/max/迟到/丢执行）与 `health` 的
  CPU/窗口读数；本会话已验证 2000 Hz 基线、`ring_drop=0`、`drop=0`。
  仿真侧测不到，因为 SIL 的循环是确定步长的，没有中断与 flag 合并。
- **舵机中位/半行程**：靠断动力地面通电标定（CTL-008 §7 的静态标定步骤），
  仿真无法替代。

> 这份盘点的用途：改代码前先看目标项属哪一档。标「弱」的项**没有机器兜底**，
> 改它必须上实机确认——不能因为 `verify-all` 全绿就以为安全。

## 3 口径提醒
- **共轴必须用 rigorous plant**：`run_coaxial_acceptance.sh` 与 `run_coaxial_suite.sh`
  的 L1 集总 plant 俯仰/姿态约定有误，会误报 `max_pitch≈23°`；用 L1 结果判共轴无效。
- **`final_alt` 判据是 8–11 m，不是「接近 10 m」**：两端都有边界，
  偏低说明定高环没拉住，偏高说明过冲未收敛。
- **失效保护矩阵的 `land_t` 必须为负**：plant 一旦触地就判失败，避免
  「掉到地上但高度指标还勉强够」的假通过。

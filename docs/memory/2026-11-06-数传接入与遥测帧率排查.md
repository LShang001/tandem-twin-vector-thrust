# 2026-11-06 单涵道数传接入与遥测帧率排查（结论已修正）

## 硬件

单涵道专用数传 = **微空 LR24**（2.4 GHz LoRa/FLRC 跳频电台），
接在荣耀本 **COM6（CP2102, VID:PID=10C4:EA60）**，921600 baud 直连固件 Serial6。

手册要点见 `docs/08-参考资料/notes/09-LR24数传电台要点.md`。关键三条：
- 透传速率档位 **2.4K / 4K / 8K / 20K Byte/s**（默认 2.4K；**"20K" 是 20 KB/s = 160 kbps**，不是 20 kbps）
- 20K 档改用 **FLRC** 调制，要求串口 **921600**
- 飞控端频点模式应配 **FHSS-AIR**，电脑端 FHSS-GROUND（默认"自动"）

## 最终结论：链路本身一直是好的，21 Hz 是测量脚本的 bug

### 真相

`GCS/server/anocom.py::extract_frames(buf)` 是**流式**接口，返回 `(frames, consumed)`，
调用方必须把跨块的半帧留在缓冲里：

```python
buf += chunk
frames, consumed = extract_frames(buf)
buf = buf[consumed:]        # 半帧留在 buf 等下一块
```

排查期间我写成了 `extract_frames(chunk)` 并**丢掉了 consumed 返回值** ——
每个 1024/512 B 读块边界上的帧全被丢弃，正好漏掉约一半。
于是把「20Hz 测成 9.91Hz」「设计 400 帧/s 测成 21.24Hz」误判成链路带宽不足，
白白改了一轮固件分频。

### 用独立方法交叉验证后的实际数据

修正后的 `TandemVec_FCS/tools/measure_link.py`（正确流式用法）实测 20 s：

| 功能码 | 实测 | gap 均值 |
|---|---|---|
| 0x01 姿态 / 0x03 欧拉 / 0x0A 目标 / 0x21 控制 / 0xF1 执行器 | **20.00 Hz** | 49.9 ms |
| 0x08 位置 | **5.00 Hz** | 199.9 ms |
| 0xF4 / 0x40 / 0x05 / 0x06 / 0x07 / 0x20 / 0x0B | **2.00 Hz** | 499.7 ms |
| 0xF5 链路 / 0x30 状态 / 0x0D 电池 | **1.00 Hz** | 999.1 ms |

总 122.0 帧/s，**校验通过率 100.0%**，帧头地址全部 `S=0x05 → D=0xFF`（与匿名助手协议一致）。

### 协议核对（匿名助手 2.0.11）

- 帧结构 `0xAB | S_ADDR | D_ADDR | ID | LEN(u16 LE) | DATA | SC | AC` 完全对齐
- 全部下发帧 S_ADDR=0x05、D_ADDR=0xFF，`extract_frames` 的 `AB 05 FF` 匹配正确
- `0x01/0x03/0x08/0x0A/0x21/0x40/0xF1` 均为官方定义；`0xF1` 用灵活格式帧承载执行器数据
- 校验为 `sum(body)&0xFF`，实测零失败

## 保留的改动：遥测降载（commit e8ff64b）

```
姿态/欧拉/目标/控制/执行器  100Hz/50Hz → 20Hz
位置                        50Hz       →  5Hz
RC / 显示组                 25Hz       →  2Hz
GPS / 氧压                  10Hz       →  1Hz
0xF4 IMU                    10Hz       →  2Hz
```

总带宽 6.9 → 1.8 KB/s。**降载是主动设计选择，不是修 bug**——理由：
1. 122 帧/s / 20Hz 姿态对地面站显示足够；
2. 若 LR24 实际仍在默认 2.4K 档，1.8 KB/s 留 25% 余量；
3. 若已配 20K 档，余量 91%，将来加视频/高程数据也有空间。

**若要更高姿态刷新率**，需先确认模块档位（微空助手读取），再把 `fast_tick` 分频调回去。

## 教训

1. **流式解析器必须传累积缓冲 + 消费游标**，不能对每个读块独立解析。这条对
   GCS 后端、抓包脚本、SIL 全部适用。
2. **测量脚本的 bug 不能当成产品缺陷**。判定链路问题前，用第二种独立方法
   （原始字节扫描 `tools/measure_link.py --raw`）交叉验证一次。
3. 本次两项独立验证（按 ID 统计 + 原始扫描）结论一致，才敢下"链路正常"的判断。

## 遥测分组重构（commit 17b71e9）

### 原结构的问题

核心飞行状态被挤在低频档：`0x05` 模式/解锁、`0x06` 速度、`0x07` 高度、
`0x20` PWM 全部捆在 `disp_tick` 一个 2Hz 档里；电池 `0x0D` 埋在 `gps_tick`
的 1Hz 档里。起飞瞬间地面站看不出状态变化。

### 新分层（t = 200Hz 计数）

| 分组 | 频率 | 分频 | 帧 |
|---|---|---|---|
| fast_tick | 50Hz | t%4==1 | 0x01 IMU / 0x03 欧拉 / 0x21 控制 / 0xF1 执行器 / 0x0A 目标姿态 |
| state_tick | 20Hz | t%10==3 | 0x05 模式解锁 / 0x06 速度 / 0x07 高度 |
| pos_tick | 10Hz | t%20==2 | 0x08 位置 |
| bat_tick | 5Hz | t%40==4 | 0x0D 电池/氧压 |
| rc_tick | 5Hz | t%40==6 | 0x40 遥控 |
| disp_tick | 2Hz | t%100==8 | 0x20 PWM / 0x30 目标速度 |
| gps_tick | 1Hz | t%200==10 | GPS |
| — | 5Hz | fast_aux/10 | 0xF4 IMU 健康 |
| — | 1Hz | t%200==1 | 0xF5 链路诊断 |

### 上板实测（COM6，20s）

```
总帧 6529 = 326.4 Hz  校验通过 6528  失败 1（99.98%）
0x01/0x03/0x0A/0x21/0xF1  47.85 Hz  gap 20.0 ms
0x05/0x06/0x07            19.15 Hz  gap 50.0 ms
0x08 位置                   9.60 Hz  gap 99.9 ms
0x0D 电池                   4.80 Hz  gap 199.9 ms
0x40 遥控 / 0xF4            4.75 Hz  gap ~200 ms
0x20 PWM / 0x0B 姿态速率     1.95 Hz  gap 499.6 ms
0xF5 / 0x30                 1.00 Hz
```

总带宽约 6.4 KB/s（52 kbps），**校验率 99.98%，证明模块确实工作在 20K 档**
（若在 2.4K 默认档，这个量级会大面积丢帧）。此前 21 Hz 的悬案到此结案：
纯粹是测量脚本漏计，链路与模块一直正常。

`0x0B 姿态速率` 仍在 2Hz 档未提升——它是调参观察量，而 0x01 帧本身已含
三轴角速度（50Hz），信息不缺失，保留低频即可。

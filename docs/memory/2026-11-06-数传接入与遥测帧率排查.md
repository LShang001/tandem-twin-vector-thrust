# 2026-11-06 单涵道数传接入与遥测帧率排查

## 硬件变更

用户新接单涵道专用数传，落在荣耀本 **COM6（CP210x, VID:PID=10C4:EA60）**，
921600 baud 直连固件 Serial6（USART6）。此前只有 USB（COM11, CH343）可用，
COM9（CH340）/COM10（DAPLink VCP）全程无数据。

## 修掉的回归（b34a9b8 → 197eb79）

此前为「无数传时也能测采样率」，把 0xF4 镜像了一份到 USB（Serial8）。
上板后出现**每 45 秒一次 3.2 秒大停顿**（所有功能码 max gap 3289 ms）。
回退该镜像后 max gap 降到 101 ms，停顿消失。

教训：**同一帧跨两个串口重复发送会拖慢主循环**，即使单口带宽只有 13% 占用。
0xF4 只发 Serial6。

## 未解决：遥测帧率只有设计的 1/4～1/2

纯监听 45 s 实测：

| 功能码 | 设计 | 实测 | gap p50 | gap p99 |
|---|---|---|---|---|
| 0x01/0x03 | 100 Hz | 21.24 Hz | 47.8 ms | 58.4 ms |
| 0x0A/0x21/0x08/0xF1 | 50 Hz | 21.24 Hz | 47.8 ms | 58.4 ms |
| 0xF4 | 10 Hz | 9.13 Hz | 95.8 ms | 326.5 ms |

已排除三项：
1. **调度正常**——tasks 表所有 200 Hz 任务实测 199 Hz，AnoCom 任务本身 199 Hz；
2. **无丢帧**——`health` 的 `ano_skip=0 proto_drop=0 mav_skip=0`；
3. **带宽不饱和**——921600 baud 下 300 帧/秒 ≈ 13% 占用。

`handleAnoCom` 内是 `const uint32_t t = s_tele_tick++;`，理论上 200 Hz 任务 →
`fast_aux_tick`（t%4==1）应 50 Hz、`fast_tick`（t%2==1）应 100 Hz。
实测两者都是 21.24 Hz，说明 `handleAnoCom` 有 89% 的拍**在 `s_tele_tick++` 之前就 return 了**。

下一步查：DBG 扫描循环（`while (Serial6.available())` peek/read）在数据密集时是否
长时间占用、或 `AnoCom.rxStalled()` 门控导致的提前返回。

**影响**：地面站刷新率只有设计值一半以下，飞行中姿态/控制显示滞后；不影响飞控
（控制环 200 Hz 独立、采样 2 kHz 正常）。

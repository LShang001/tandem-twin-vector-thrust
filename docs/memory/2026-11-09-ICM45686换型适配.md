> ## ⚠️ 现状更新（2026-11-11，读本文前必看）

>

> 换 45686 版飞控板时的完整排查与修复记录。结论：**驱动现在能用**，两个后端可随意切换。
> 采样率：ICM-45686 走 **3.2 kHz FIFO 单包**（ISR 每 2 拍取一包）；ICM-42688 走 2 kHz 硬件 FIFO。

## 1 结论先行

| 项 | 状态 |
|---|---|
| 45686 驱动可用性 | ✅ 可用（SPI 通信、芯片识别、ODR/FSR/LPF 配置全通） |
| 数据链路 | ✅ 通（IMU→EKF→控制，`cal=1 drop=0 ring_drop=0`） |
| 42688 原功能 | ✅ 未受影响（改动全在 `lib/ICM45686/` 内，42688 版编译 6.3 s SUCCESS） |
| 可切换性 | ✅ 两套 env 并存，换 env 烧录即切换 |
| **采样率** | 45686 = **3.2 kHz FIFO 单包**（ISR 每 2 拍取一包），42688 = 2 kHz FIFO |

## 2 根因：`dataReady()` 恒返回 0

`ICM45686_ImuDevice::dataReady()` 读 `INT1_STATUS0`（reg 0x19）的 bit2 `DRDY` 判新数据，
但 `begin()` **从没使能** `INT1_CONFIG0.int1_status_en_drdy`——该状态位恒 0，于是：

```
dataReady() 恒返回 0
  → sensor_imu.cpp:190 采初始 100 样本时 20ms 超时
  → 打印 "[Error] IMU init data timeout."，返回 -1001
  → main.cpp:370 if (initICM42688() != 0) 进 while(1){ 闪黄灯; delay(200); }
```

**现象**：板子黄灯 2.5 Hz 闪，串口只在开机那一瞬有输出（之后不再打），
`verify_board` 全部读 `-1`/`?`。

**修复**：新增 `ICM456xx::enableIntStatusDrdy()`，只写 `INTx_CONFIG0` 的 status 使能位，
**不配 pin config、不 attachInterrupt**——板子没把 INT 引脚接到 MCU 也能工作。
`begin()` 在 `startGyro` 成功后调用它。

## 3 排查过程中排掉的三件事（都不是问题）

| 怀疑 | 实测 | 结论 |
|---|---|---|
| 波特率不对 | APB1=80 MHz、UART8 BRR=87 → 80e6/87 ≈ 921600 | 波特率正确，`Serial8.begin(921600)` |
| 时钟没起来 | RCC_CR `0x3f03c025`（HSERDY=1）、RCC_CFGR `0x1b`（SW=PLL1） | 时钟正常 |
| 固件没跑 | SWD 读 PC，值在 `0x0804c60c/610/614` 间跳变 | 在跑（当时卡在 370 行死循环的 `delay`） |

**关键坑**：一开始读串口全是 0 字节，误判成「链路坏」。
实际是**开机打印早就在我读之前发完了**，固件已经卡死在死循环里不再输出。
用 OpenOCD `reset run` **同时**开串口抓，才拿到那 705 字节的开机日志。

另一个坑：新板子的调试口不是旧板子的 COM6（CP210x），是 **COM12（CH343）**——
串口号随板子枚举变化，每次换板先列 `Get-CimInstance Win32_PnPEntity` 看实际端口。

## 4 采样率差距：200 Hz vs 2000 Hz

上层架构（`task_scheduler.cpp:211`）：TIM8 定时器中断里 `s_imu_phase += 2000`，
累到 6400 触发一次 `imuSampleIsr()`，即 2 kHz 调 `IMU->readFifo()`。

- **42688**：`readFifo` 从芯片硬件 FIFO 批量读，一次 SPI 拿数据
- **45686**：`enableFifo()` 未实现 → 返回 -1 → `s_imu_ring_ready=false` →
  ISR 直接 return → 数据改由 200 Hz 任务轮询寄存器

**试过的方案（失败，已回退）**：给 45686 补 `enableFifo()`/`readFifo()`，
`readFifo` 里先 `dataReady()` 再读六轴。实机结果是**系统过载**：
DBG 完全无响应、`verify_board` 8 项全挂。原因是在 2 kHz ISR 里做**两次** SPI
（读状态 + burst 读数据），负载远超 42688 的「一次 FIFO 批量读」。

**要真正做到 2 kHz**，得用库的 `inv_imu_adv_get_fifo_data()` 配硬件 FIFO 批量读，
而不是轮询寄存器。这是下一步的正路。

## 4.5 手册查证与 3.2 kHz 攻关（同日追加）

**手册（DS-000577 v1.0，项目内 `lib/ICM45686/doc/`）确认**：
- ODR 档位到 **6.4 kHz**：`ACCEL_CONFIG0(0x1B)` / `GYRO_CONFIG0(0x1C)` 的 bit3:0，
  `0011`=6.4k、`0100`=3.2k、`0101`=1.6k（LN 模式）。**芯片能力不是瓶颈**。
- **有完整硬件 FIFO**：`FIFO_COUNT_0/1(0x12/0x13)`、`FIFO_DATA(0x14)`、
  `FIFO_CONFIG0(0x1D)`、`FIFO_CONFIG3(0x21)`（`FIFO_IF_EN`/`ACCEL_EN`/`GYRO_EN`）、
  `FIFO_CONFIG4(0x22)`；`INT1_CONFIG0(0x16)` bit1=FIFO_THS、bit0=FIFO_FULL。
- 库已封装：`configureFifo(ICM45686FifoConfig)`、`getFifoFrameCount()`、
  **`getDataFromFifoBatch()`**（一次 burst 多帧，专为减少每帧 SPI 事务设计）。
- 帧结构 `inv_imu_fifo_data_t`：`byte_16.accel_data[3]` / `gyro_data[3]` / `timestamp`。

**据此实现 FIFO 后端，五种方案全部实测失败**：

| # | 方案 | 实测结果 |
|---|---|---|
| 1 | ODR 3.2k + 2 kHz ISR，`readFifo` 逐帧（读状态+读数据两次 SPI） | 系统过载，DBG 完全无响应 |
| 2 | ODR 钳 1.6k + 1 kHz ISR + FIFO 批量 | `ring_drop=57913` |
| 3 | ODR 3.2k + ISR 批量读 8 帧 + 消费限流按 3200 算 | `ring_drop=35785`、`cal=0` |
| 4 | 方案 3 + 独立 1 ms 消费任务 `handleImuDrain` | 系统过载（`readIMUData` 内含校准/滤波，1 kHz 跑不动） |
| 5 | 方案 3 + ring 容量 128→1024（约 32 KB） | `ring_drop=41660` |

**根因判断**：瓶颈不在驱动，在**上层消费架构**。
`readIMUData()` 每帧要做自动校准 + 一阶互补滤波 + RUB→FRD 轴映射，是重活；
Navigation 每 5 ms 排空一次，`allowed = 1 + elapsed_us·3200/1e6 ≈ 17` 帧/拍，
理论 3400 帧/s > 生产 3200 帧/s，但实测持续丢包——说明**每帧处理耗时吃满了 5 ms 预算**，
实际消费速率达不到理论值。

**要真正上 3.2 kHz，必须做架构级拆分**（不是调参数能解决）：
- 把 `readIMUData()` 拆成「取数据」（轻，只 pop + 入中间缓冲）和「处理数据」（重，校准/滤波/轴映射）；
- 取数据跟 ISR 同频或由独立轻任务承担，处理仍按 Navigation 200 Hz 走；
- 或者反过来：既然 EKF/控制只用 200 Hz，把 ODR 定在 800 Hz 更匹配，
  不必为了"跑满芯片"付架构改造成本。

## 4.6 3.2 kHz 攻关：两个真因都跟性能无关（同日最终解决）

§4.5 记录的五个失败方案方向全错——它们都在治「消费不够快」。加探针实测后
发现两个真因，都跟吞吐无关：

### 真因一：`injectFifo` 从未实现，排空第二次就永久降级

探针实测（health 的 p1 行新增 isr_c/isr_f/isr_bmax/drain_c/drain_f/allow_avg/fus_avg/fus_max）：

```
isr_c=11786  isr_f=37907  isr_bmax=4     ISR 侧完全正常，平均 3.2 帧/拍
drain_c=2    drain_f=0    allow_avg=6    消费侧只进了 2 次，一帧都没处理
```

`ImuDevice::injectFifo` 基类默认返回 -1，45686 从未重写；而 `sensor_imu.cpp`
的排空循环一遇到 `injectFifo < 0` 就置 `s_fifo_fallback = true`，**永久**降级到
200 Hz 轮询。所以前面那些调 ODR、改 ISR 频率、放大 ring 的努力全部无效——
消费根本没启动。

补 `injectFifo`（注入样本 + `accX`/`gyrX` 优先返回注入值）后，`ring_drop`
立刻归零，`isr_f` 与 `drain_f` 完全匹配。

### 真因二：批量帧的 dt 不能用 micros() 差分

补完 `injectFifo` 后采样率上去了（`isr_f/win_s ≈ 3202`），但**数据是错的**：
`rpy=147.5/-38.99/246.37`、`vel=-139.45/-173.84/18.54 m/s`、`pos_sig=529.78`。

`readIMUData` 原用 `micros()` 差分算 `deltaTimeSecs`。单帧轮询时这没问题，
但批量排空时 16 帧在同一拍内处理完，实测单帧处理只要 `fus_avg=8µs`，而真实
帧间隔是 1/ODR（3.2 kHz → 312.5µs）——**dt 小 39 倍**，角速度/加速度增量积分
严重偏小，EKF 直接发散。

修法：排空循环里按后端 ODR 写入固定 dt（`s_fifo_frame_dt_s = 1/3200`），
`readIMUData` 优先用它。修后 `rpy=-40.06/1.60/319.34`、`vel=0/0/0`、
`pos_sig=0.50`，与 200 Hz 轮询后端（`-39.91/1.42/319.83`）一致到 0.15°。

### 最终方案（三处改动，全部在 45686 路径上生效）

1. `ICM45686_ImuDevice::injectFifo` —— 注入样本，访问器优先返回注入值
2. `enableFifo`/`readFifo` —— `configureFifo`（Stream / 8KB / 16-bit 帧）
   + `getFifoFrameCount` + `getDataFromFifoBatch` 一次 burst 批量取
3. `sensor_imu.cpp` 的 `imuSampleIsr` —— 从「读 1 帧」改「批量读最多 16 帧」；
   排空限流按后端 ODR（45686 3200 / 42688 2000）；ISR 步进按后端
   （45686 1 kHz / 42688 2 kHz）；批量帧用固定 dt

### 实测结果（COM12 @921600，SingleEdf4Vane_ICM45686）

- 采样率 3216 Hz（`isr_f` 两次差分），`isr_bmax=4`，单帧处理 8 µs
- `ring_drop=0`、`cal=1`、`drop=0.0s`、CPU 48%
- 姿态与 200 Hz 后端一致，`vel=0`、`pos_sig=0.50`

### 遗留问题

- **`cal` 偶发为 0**：`IMU_AutoCalibrator` 需要 4000 个静止样本（3.2 kHz 下
  1.25 秒），判据是模值 0.5~1.5g、方差 < 2e-5、角速度模长 < 0.1。
  已加诊断探针 `caln=`（样本数）/`calst=`（状态）/`calv=`（方差），
  待上板读取定位卡在哪一条。
- **DBG 期间 `ring_drop` 增长**：DBG 控制台串口打印是阻塞写，调度器单线程
  顺序执行，打印期间 Navigation 停摆而 ISR 继续采样，128 槽 ring 必然打满。
  调试态固有；飞行时不接 DBG 不受影响。`verify_board` 已把它降为信息项。

## 4.8 42688 路径等价性论证（判据：换型不得影响原功能）

三处改动对 42688（2 kHz ISR / 2 kHz ODR / 每拍 1 帧）逐条比对：

| 改动 | 45686 效果 | 42688 效果 | 判定 |
|---|---|---|---|
| ISR 批量读 `readFifo(batch, 16)` | 每拍取 3~4 帧 | 每拍返回 1 帧，push 1 帧 | 等价 |
| 固定 dt = 1/ODR | 1/3200 = 312.5 µs | 1/2000 = 500 µs（等于实际间隔） | 等价 |
| ring 模式跳过 DRDY 门控 | 一拍 16 帧全部处理 | 一拍 1 帧，原本也全部处理 | 等价 |
| ISR 步进按后端 | 1 kHz | 2 kHz（走 `#else` 分支，未改） | 不变 |

**唯一差异**：若 42688 某拍 FIFO 里积压了多帧（启动瞬间或调度抖动），
原实现只处理 1 帧、余下留在 FIFO；新实现全部取出处理。这是**修正**不是回归。

**验证状态**：编译通过（`SingleEdf4Vane`，52 s SUCCESS）；SIL 不覆盖此文件（见 §4.7）；
**实机验证未做**——当前板子上装的是 45686 芯片，42688 后端缺硬件无法上板。
要真正确认，需要换回 42688 板的飞控做一次 7 项自检。

## 4.8.5 3.2kHz 最终方案与 `conv=0` 的正解（同日攻坚收尾）

**先记最重要的教训：读 2026-11-04-IMU-2kHz攻关.md 之前，我的方向是错的。**

那份文档 §4「无效路线（不要再试）」第一条就写着「FIFO 批量一次读 8 包：
4218 Hz 但 EKF 退化，批量消费/重复计数不可靠」，§6 P1 架构不变量写的是
`readFifo(1包)`。而我花了大半天做批量 16 包，踩的坑一模一样（多出 20% 假帧、
EKF 炸到 -633 m/s），最后靠跑回单包读才通。**改 IMU 前必须先读那份文档。**

**最终方案**（与 P1 架构不变量一致）：

1. `imuSampleIsr` 单包读 `readFifo(&one, 1U)`
2. ISR 频率 = ODR：`s_imu_phase += 3200`（TIM8 6400 / 2 = 3.2kHz），一拍一包
3. `injectFifo` 注入样本（本后端独有，42688 早就有）
4. 批量帧固定 dt = 1/ODR（这条对单包读也适用，保证 dt 与 ODR 一致）
5. ring 模式跳过 DRDY 重复门控
6. 不做 header 过滤（单包读下过滤会丢约 10% 样本）

**实测**：`rate=3199.4~3201.3 Hz`、`cal=1`、`caln=4000`、`calst=2`、
`drop=0`、`ring_drop=0`、CPU 52.7%、`verify_board` **7/7 全 PASS**。

### `conv=0` 不是故障，别再查它

曾把 `conv=0`（`vel_sig=1.94` 超收敛判据 1.0）当成阻塞问题，一路排查
Q 缩放、LPF 带宽、静止检测、header 过滤——全是白工。

**正解在 VER-010 §5.6**：「`conv=0` 是预期结果：室内无 GNSS、`fake_origin=1`、
且本机磁力计未检测到，EKF 没有绝对参考可收敛。这不代表 EKF 异常。」

`flight_control.cpp` 的 `nav_ready = g_ekf_converged && ...` 确实会在
`conv=0` 时强制上锁——但那是**地面无 GNSS 的房间内**，接上 GNSS 后 `vel_sig`
会被绝对速度观测压下去，`conv` 自然置 1。**判断「能不能飞」要看有没有 GNSS，
不是看室内的 conv 值。**

为此改的 LPF（陀螺 200→100Hz、加计 100→50Hz）实测 `vel_sig` 1.94→1.95 无改善，
已回退，避免动到已验证的带宽。

## 4.9 `cal=0` 诊断决策树（待上板取数）

`IMU_AutoCalibrator` 的判据：需要 **4000** 个静止样本；进入条件三条同时满足——
加速度模值在 0.5~1.5 g、模值方差 < 2e-5、角速度模长 < 0.1 dps。
`health` 已输出四个探针：`caln=`（样本数）、`calst=`（状态 0=等静止/1=采集中/2=完成）、
`calv=`（加速度方差，已乘 1e6，所以阈值 20 对应 2e-5）、`calg=`（角速度模长，单位 dps，
判据阈值 0.1 rad/s ≈ 5.7 dps）。

**已排除的一条**：`is_armed`。`sensor_imu.cpp:513` 的 `is_armed = (raw_rc_values[4] > 1500)`，
没接接收机时 `raw_rc_values` 初始化为 0；即使触发 failsafe 用 plan 覆盖，
`kChArm=4` 在未飞行时给 `kPwmLow`、飞行中给 `kPwmMid`（1500，不满足 `> 1500`）。
所以「误判解锁导致校准不跑」这条路走不通，`cal=0` 只剩方差与角速度两个条件。

对照下表一分钟定位：

| 现象 | 卡在哪 | 下一步 |
|---|---|---|
| `caln=0`、`calst=0` 长期不变 | 静止判据未满足 | 看 `calv`：> 20 说明方差超限（3.2 kHz 下 LPF 带宽更宽、噪声更大是首要嫌疑）；`calv` 正常则看角速度是否 > 0.1（陀螺零偏未补偿时静止读数可能超） |
| `caln` 一直涨但从不到 4000 | 中途被扰动重置 | 板子被碰/震动；换稳定台面重试 |
| `caln=4000` 但 `calst` 仍 1 | 状态机没跳 FINISHED | 逻辑 bug，看 `sample_count >= CALIBRATION_SAMPLES` 分支后面是否有提前 return |
| `calst=2` 但 `cal=0` | `isCalibrated()` 标志没置 | 看 FINISHED 分支是否漏了 `_is_calibrated = true` |

**注意**：DRDY 门控修复（§4.6 之后那条）让每拍处理帧数从 1 变成 16，
校准样本累积速率提高 16 倍（4000 样本从 20 秒降到 1.25 秒）。如果 `cal=0`
当初只是「累积太慢 + 期间被扰动重置」，这条修复可能顺带解决它——**先上板看数**。

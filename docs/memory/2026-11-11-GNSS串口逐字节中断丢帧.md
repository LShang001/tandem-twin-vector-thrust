# GNSS 串口丢帧根因：逐字节中断 + 1 字节 RDR（2026-11-11）

> **触发条件**：排查 GNSS 定位跳变/丢历元、ubxstat 出现 `eoe_no_pvt`/`bad_pvt`
> 偏高、改 GPS 串口波特率或接收方式时；任何 921600 及以上波特率的串口丢字节问题。

## 判据（ubxstat 直接看）

- `eoe_no_pvt`：EOE 历元数 − 配到有效 PVT 的历元数。实测修复前每秒约
  0.7 个历元无 PVT（8Hz 下 **9.8%**）。
- `bad_pvt` = `pvt_checksum_fail_count()`：PVT 帧**校验失败**（字节级损坏）。
- `cksum_fail`：任意 UBX 帧校验失败。
- 三者同时升高 = 串口层丢字节，不是 GNSS 卫星或解算问题。

## 根因

框架 `framework-arduinoststm32` 的 `uart.c` 用
`HAL_UART_Receive_IT(huart, &obj->recv, 1)` —— **每次中断只收 1 字节**，
且 STM32 的 RDR 只有 1 字节深（H7 的 16 字节 FIFO 默认关闭）。

921600 波特率下每字节 **10.85 µs**。只要 UART4 中断等待一次
（TIM8 6.4kHz ISR、SPI 读 IMU、其他串口），RDR 就溢出，`ORE` 标志被
`ClearFlag_ORE` 清掉、字节永久丢失 —— 帧内丢 1 字节即整帧校验失败。

补充事实：UART4 中断优先级已是 0（最高），TIM8 是 3，**不存在抢占不足**；
瓶颈是逐字节模式本身。去掉接收机冗余消息（带宽 1822→1555 B/s）也不改善，
进一步证明与带宽无关，只与 RDR 深度有关。

## 修复（两处，已上板验证）

1. **启用 UART4 硬件 FIFO**（`src/main.cpp`，`Serial4.begin` 之后）：
   ```cpp
   UART4->CR1 |= USART_CR1_FIFOEN;   // H7 的 16 字节 RX FIFO
   ```
   只置寄存器位、**不重调 `HAL_UART_Init`**（会打断接收）。HAL 在 FIFO 模式
   下用 `RXFNE`(=RXNE) 判据，逐字节读取逻辑不受影响。容忍窗口
   10.85 µs → **约 174 µs**。
   ★ 外设名是 `UART4` 不是 `USART4`（H743 编译报未声明）。

2. **关闭接收机冗余消息**（`src/ubx_config.cpp` 的 `ubxAutoConfig`）：
   原实现只开 NAV-PVT/NAV-EOE，从不关闭出厂默认的其余消息（实测占约 56%
   带宽）。补 `rate=0` 关闭 NAV-POSLLH/STATUS/DOP/SOL/VELNED/TIMEUTC/
   CLOCK/SVINFO/SAT/SIG。

## 实测效果（同约 75 s 窗口）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `eoe_no_pvt` 丢失率 | 9.8% | **5.3%** |
| `cksum_fail` | 129 | **34** |
| `bad_pvt` | 72 | **29** |
| `bad_other` | 57 | **5** |
| `frame_timeout` | 20 | **2** |
| `pvt_dup` | 76 | **7** |

GNSS 解算未受影响（`fix=4`、`age_ms=122`、`pvt`/`eoe` 正常推进）。

## 剩余 5.3% 的定性

仍是字节级损坏（`bad_pvt` 3.9%）+ 完全丢帧（1.4%）。要根除必须改用
**DMA 接收**（`HAL_UART_Receive_DMA` + IDLE 中断），那要改框架接收架构、
影响全部串口，属于独立改动。当前 8Hz × 5.3% ≈ 每秒 0.4 个历元丢失，
EKF 侧有量测外推补偿，不构成起飞阻塞。

## 顺带纠正

「卫星少/精度差」与「丢帧」是两个独立问题：前者看 `fix`/`sv`/`hacc`
（本例 `sv=6`、`hacc≈9~13m` = 天线环境），后者看 `eoe_no_pvt`/`bad_pvt`。
混在一起会误判成固件缺陷。

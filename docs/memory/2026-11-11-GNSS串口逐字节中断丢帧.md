# GNSS 串口校验失败与丢历元定位（2026-11-11 起，2026-11-17 修复）

> **触发条件**：排查 GNSS 定位跳变/丢历元、`ubxstat` 的 `eoe_no_pvt`/`bad_pvt`
> 偏高，改 GPS 串口波特率、FIFO、接收方式或 WS2812 DMA 发送时。

## 判据（ubxstat 直接看）

- `eoe_no_pvt`：EOE 历元数 − 配到有效 PVT 的历元数，反映缺完整历元。
- `bad_pvt` / `cksum_fail`：PVT / 全部 UBX 帧校验失败，反映字节流损坏。
- `frame_timeout`：半帧悬挂后超时，反映帧内断流。
- `fifo_hw / fifo_hal / irq / cfg_fail`：UART4 硬件 FIFO、HAL FIFO 状态、
  中断优先级和配置失败次数。正常值分别为 `1 / 1 / 0 / 0`。
- `queue_overflow=0` 只表示 UBX 历元队列没溢出，**不能排除硬件 ORE、
  串口环丢字节或线路位错误**。验收必须做计数差分，不只看累计值或 `fix=3`。

## 根因

1. 框架 `uart.c` 用 `HAL_UART_Receive_IT(...,1)` 逐字节接收。921600 波特率下
   每字节仅 10.85 µs；只在早期写 `UART4->CR1 |= FIFOEN` 不足以可靠覆盖。
2. `Uart::begin()` 会重跑 UART 初始化，清除 FIFOEN 并恢复框架默认中断优先级。
   GNSS 自动配置在 `setup()` 后段再次 `begin()`，因此早期设置的 FIFO 和优先级
   会被覆盖。直接置 FIFOEN 也没有同步 HAL 句柄，不能当作完整配置。
3. WS2812 驱动曾在 `noInterrupts()` 内调用 `HAL_DMA_PollForTransfer` 等待整帧，
   单灯约 130 µs、100 Hz。它会同时屏蔽最高优先级 UART4，使未有效配置的
   逐字节接收发生溢出。

## 修复

- 新增 `ubxGnssSerialBegin()`，GNSS 上电、自动探测、切速和 `gpsproto` 改波特率
  统一走该入口：停止旧接收事务 → `HAL_UARTEx_EnableFifoMode()` → 设置 1/2 FIFO
  阈值 → 用原接收地址重启 1 字节 IT → 恢复 UART4 优先级 0。读回硬件、HAL 和
  接收状态，失败累计到 `cfg_fail`。
- WS2812 的 DMA 等待不再关闭全局中断，保留 DMA 状态清理与 50 ms 超时保护。
- 不修改 UBX 校验算法，不放宽任何校验或门控。

## 实测（CoaxialVTVL_ICM45686，静止、未解锁）

- 首轮连续 3539 个历元：`cksum_fail=0`、`bad_pvt=0`、`eoe_no_pvt=0`、
  `frame_timeout=0`、`queue_overflow=0`。
- 自动配置重跑和 `gpsproto auto 921600` 后，读回 `fifo_hw=1 fifo_hal=1 irq=0
  cfg_fail=0`，坏帧仍为零。
- 严格差分脚本再连续观察 120 s，所有错误计数无新增。

## 可复用验收

在接飞控 Serial6 的机器上运行：

```bash
py -3.13 tools/verify_gnss_stream.py --port COM9 --seconds 120
```

脚本自动进入/退出 DBG，只读 `ubxstat`。判据为：观察窗口内校验失败、坏 PVT、
缺历元和帧超时均无新增，FIFO/HAL/优先级持续有效，PVT/EOE 持续前进。
不能将 DBG 下的任务瞬时耗时直接当作非 DBG 的飞行负载。

## 边界

- 现有证据支持先修串口配置与全局屏蔽，**不需要为解决这类校验失败改造整个
  框架的 DMA 接收架构**。若修后仍出现字节错误，先补硬件 ORE/FE/NE 与串口环
  丢弃计数，再决定是否需要 UART4 专用 DMA。
- 卫星数量与 `hacc` 是天线/环境问题，与串口字节完整性分开判断。
- 本结论只覆盖静止、未解锁、正常 GNSS 输出工况，不外推为实飞振动或电磁
  环境下永久零误码。

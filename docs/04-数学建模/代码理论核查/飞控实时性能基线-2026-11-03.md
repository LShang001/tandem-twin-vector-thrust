## 2. 可疑现象：200 Hz 任务实际约 155 Hz

`tasks` 统计窗口 13.672 s，Navigation/GNC/CAN 的 `cnt=2125` →
**155.4 Hz**，而注册周期是 5 ms（200 Hz）。同一窗口 IMU `cnt=14331`
（约 1048 Hz 平均）。

**机理假设（待上板用 `迟到` 列确认）**：调度器是“定时器置 flag + 主循环消费”
的合并式调度；若一次主循环 pass 内同时到期多个 5 ms 任务（它们注册相位几乎
相同），本次 pass 可能超过 5 ms，期间定时器再次置位只会把 flag 保持为 true，
下一次 pass 只执行一次 → 实际频率下降。`max pass=3388 µs` 已接近 5 ms，
加上 Flash 写页/CAN 偶发 800 µs，足以造成漏拍。

**验证方法**：`DBG tasks` 看每个任务的 `迟到` 计数与 `间隔max`；若
`迟到 > 0` 且 `间隔max` 明显大于 5 ms，则确认“相位同步导致漏拍”。

**候选修复（未实施，属调度/频率改动，需专项批准）**：
1. 任务注册时按任务序号加 1–2 tick 相位偏移（`BFS_TASK_PHASE_STAGGER`），
   把 7 个 5 ms 任务摊到 5 ms 窗口内，不改变名义频率；
2. 把 Navigation 的 1.5 ms 再压缩（DTCM/算法）；
3. CAN 改为单事务 `sendMsgBuf` 或 INT 门控轮询（当前 476 µs 主要花在
   MCP2515 多次 SPI 状态读/写）。

## 3. 已确认的优化/非优化项

| 项 | 结论 |
| --- | --- |
| `-O3` | 已在 `platformio.ini` 启用 |
| I/D Cache | Arduino `premain()` 已开；**不要在 setup 重复开**；复位后 halt 读 CCR 是假象 |
| 协方差 float | 已启用 `BFS_NAVIGATION_EMBEDDED_FLOAT_COVARIANCE=1`，cov_avg 5.20→0.97 ms |
| DTCM | 已提供 `[env:TandemVec_FCS_DTCM]`（`BFS_NAV_EKF_DTCM` + 链接段），`nav_ekf` 落在 0x20000000；待上板 A/B，默认不启用 |
| ITCM | 64 KB 未用；需链接脚本拷贝段，风险高，暂缓 |
| IMU ODR | 实测 1200–1360 Hz；提高 ODR 会增加 IMU 任务负载，需与 200 Hz 控制率一起评估 |
| 任务相位 | 已提供 `[env:TandemVec_FCS_PHASE]`（`BFS_TASK_PHASE_STAGGER`），只错开 ≥5ms 任务的首次相位；待上板看迟到列 A/B |
| 控制率 | 200 Hz 注册；是否提高属安全关键频率改动，禁止未批准修改 |

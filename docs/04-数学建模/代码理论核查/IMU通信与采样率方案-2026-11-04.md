# IMU 通信与采样率方案（ICM-42688-P）

## 1. 现状（先排除误判）

- 驱动 `ICM42688::getAGT()` 已经是 **一次 INT_STATUS 读 + 一次 14B TEMP/ACC/GYRO burst**；
  `accX()/gyrX()` 只是内存取值，不是六次 SPI 事务。
- SPI1 = 10 MHz，2 kHz ODR。通信时间不是 1.4 kHz 的唯一原因。
- `readIMUData()` 由协作式主循环 `handleICM42688` 轮询；名义 0.5 ms，
  但任何耗时任务都会让 flag 合并。`health`/DBG 读取时更明显。
- 实测 `imu_rate` 约 1.4–1.6 kHz（AnoVars，非 DBG）；2 kHz 标称不等于实际。

## 2. 已有但未接入的能力

- `ICM42688::enableFifoStream()` / `disableFifoStream()`；
- `ICM42688::readFifoPackets()`：Packet 3 16B/包，一次 `FIFO_COUNT` + 一次
  burst（当前最多 8 包），已按 FSR/校准换算为 g/dps；
- `imufifo` DBG 自检能读 8 个有效包；
- `imu_delta` 64 深缓冲 + 200 Hz Navigation 消费。

**没有接入飞行链路的原因**：早期按“逐包 16B 事务”试过，单次 IMU 任务
136 µs/max 531 µs，Navigation 掉到 183 Hz/max 10.3 ms；不是 FIFO 本身错，
而是读法/批量策略错。

## 3. 推荐方案（按代价从低到高）

### A. FIFO 批量读取（首选）

1. 使能 Stream-to-FIFO（accel+gyro，temp 可选）；
2. `handleICM42688` 改为 1 ms 调度（2 kHz 下每次约 2 包），一次
   `FIFO_COUNT` + 一次 ≤8 包 burst；
3. 逐包走现有单样本处理（校准/滤波/轴变换/增量/Madgwick），不要逐包发 SPI；
4. 保留 `imu_delta` 64 深缓冲，Navigation 仍 200 Hz 消费；
5. 验收：`imu_rate`≥1900 Hz、Navigation avg≤6 ms/max<15 ms、EKF 不退化、
   SIL 24/24/40/40 不回退。

### B. 数据就绪中断/水位

- 用 INT1 DRDY 或 FIFO watermark 置 flag，主循环只在有包时读；
- 不能在 ISR 里做 Madgwick/浮点大批处理；ISR 只置位/抓时间戳。

### C. SPI DMA / 提高时钟

- H7 SPI1 DMA 读 FIFO burst，释放 CPU；需改驱动与并发保护；
- SPI 10→20/24 MHz 只在信号完整性验证后做，单独提速不会解决主循环合并。

### D. 独立高优先级 IMU 任务/定时器

- 协作式调度器没有抢占；若 FIFO 仍不足，把 IMU 采集放到 TIM 中断或
  独立高优先级任务，只把样本写入 ring buffer，处理仍在主循环。
- 这是最后手段，优先用 A/B。

## 4. 判定口径

- 用 `tvc vars watch imu_rate -t 60`，不要用 `health`/`tasks` 的 DBG 读数；
- 同时看 `tasks` 的 Navigation avg/max、`imu_drop`、`imu_delta_overflow`；
- 只提升 `imu_rate` 但 Navigation max 变差，不算解决；
- 目标不是盲目追 3.2 kHz；现役 42688 的 ODR 是 2 kHz，滤波器按 2 kHz 设计。

## 5. 2026-11-04 FIFO 首次接入尝试（已回退）

按 A 方案做了最小注入式批处理（FIFO 读 ≤8 包、强制 dt=1/ODR），上板 A/B：

- `imu_rate` 显示 **4218 Hz**（不可能是 2 kHz ODR）；
- `conv=0`、`vel=1.43/0.33/2.49 m/s`、`pos_sig=11.34`，EKF 明显退化；
- 默认轮询版回退后 `imu_rate≈1263–1400 Hz`、`conv=1`。

判断：批处理的时间戳/包计数/消费速率有一致性问题，不能把“每包强制
dt=1/ODR”当作真实采样时间；也说明 `imu_rate` 本身会被重复样本放大。
实验代码和 `CoaxialVTVL_FIFO` env 已回退，飞行默认仍走轮询 UI 路径。
下次必须先用 FIFO 包时间戳/计数校验、单包注入，再逐级增加批量；不能直接
以 4 kHz 读数当成功。

## 6. “单次 status+data burst” 也失败（2026-11-04）

把 INT_STATUS + 14B 数据合并成从 0x19 一次读 18B 后，上板出现：
`imu_rate=2000.4 Hz` 但 `imu cal=0`、EKF rpy=135/35/73、fake_origin=0。
**根因不是偏移，而是地址错**：`registers.h` 定义
`UB0_REG_INT_STATUS = 0x2D`（靠近 FIFO_COUNT 0x2E），不是 0x19；
从 0x19 读 18B 实际读到配置/FIFO 区，不能这样合并。
已回退 `getAGT()` 原两次读实现，板上恢复 `imu_rate≈1402 Hz、cal=1、conv=1`。

结论：ICM-42688 的寄存器 burst 不能凭地址直觉合并；必须逐字节对照
DS-000347 的 INT_STATUS/TEMP_DATA 地址与读出时序，并用静态姿态/重力判据
验证，不能只看 `imu_rate`。

## 7. FIFO 2 包实测与下一步约束（2026-11-04）

寄存器复核：`FIFO_COUNTH/L=0x2E/0x2F`、`FIFO_DATA=0x30`，`readFifoPackets()`
也是「一次 count + 一次 burst」，没有新的地址错误。

单包 FIFO：`imu_rate≈1624 Hz、conv=1`；2 包 FIFO 非 DBG `vars watch`：
**avg=3198 Hz、min=195.8、max=3445.7**，不是稳定 2 kHz。说明每次调用实际
包数/时间戳/消费速率仍不一致，不能把读数直接当采样率。

下一步必须先加**每调用包数直方图 + 包时间戳/计数**（不改默认），确认
`n=0/1/2` 的分布与 Navigation 窗口的 delta 数；在此之前：
- 不提高 ODR；
- 不上 DMA（DMA 只改搬运，不解决重复包/时间戳）；
- 不把 2 包 FIFO 设为默认。

## 8. FIFO 包数直方图（2026-11-04 上板）

新增 DBG 命令 `imufifohist`（未解锁可用，临时开 FIFO，每 1 ms 读最多 8 包，
统计 200 次后关闭，不接控制路径）。实测：

```
calls=200 n=0/0/193/3/0/1/0/0/3 total=424 avg=2.120 elapsed=200.1ms
```

即 FIFO 产率约 **2.12 包/ms ≈ 2120 Hz**，与 2 kHz ODR 基本一致；不是传感器
输出 3.2 kHz。2 包消费版本出现 avg3198 Hz，说明问题在 **FIFO 弹出/消费计数**
（读取后指针是否真正前进、消费频率），不在产率或 SPI 带宽。

下一步：
1. 连续调用记录同一包的特征/时间戳，确认 `FIFO_DATA` 读取是否真正弹出；
2. 单包消费验证 n/时间戳，再试 2 包；
3. 弹出正常后才谈 DMA/中断；当前默认轮询路径不变。

### 8.1 时间戳判定（同日）

`imufifohist` 增加 Packet3 时间戳透出后实测：

```
calls=200 total=424 avg=2.120  ts0=60832 ts1=62506  elapsed=200.1ms
```

时间戳持续前进（不是同一包重复），因此 **FIFO_DATA 弹出正常**；2 包消费版
`imu_rate≈3198` 的问题在**消费/任务频率**（每次调用读 2 包 + 主循环调用
过密/统计口径），不是 FIFO 指针不前进。下一步应加每调用 `n` 直方图和
Navigation 窗口 delta 对账，再决定是限流、降频还是 DMA/中断。

当前时间戳透出只服务诊断；默认飞行路径仍轮询。

## 9. 隔离实验：其他任务停 vs 全调度（2026-11-04）

按“临时禁用其他任务定位”做了两组：

1. `imufifohist`（DBG 内阻塞主循环，其他任务不运行）：
   `total=424/200ms`，平均 **2.12 包/ms≈2120 Hz**，Packet3 时间戳持续前进。
   → 传感器、SPI、FIFO 弹出都正常。
2. FIFO 2 包接回主路径 + `imufifostat`：
   `calls=13434 packets=19007 n0/1/2=426/7009/5999`，平均1.415包/次，
   `imu_rate≈1900–1940 Hz`；但 `task0_period=1108µs`、`[LOOP] cpu=77.4%`、
   `Navigation max=275556µs`、EKF `vel=21.51/1.55/21.14`、conv=0。

结论：**不是 IMU 产率/通信瓶颈，是主循环消费 2 包后 CPU/导航任务被拖垮**。
提高定时器频率不会减少每包处理成本；先禁用任务已证明两边差异。正确方向：
专用高优先级采样任务/中断 ring buffer 或 DMA+FIFO，处理与导航解耦；
不能继续在 200 Hz 协作主循环里堆 IMU 处理。

## 10. 非 DBG 遥测测量（2026-11-04，用户纠正后）

**教训：高频采样/时序测试禁止用 DBG。** DBG 会暂停遥测/阻塞任务，之前
`imu_rate=3198`、`vel=21 m/s` 就是 DBG 命令造成的假象。

新增普通遥测帧 **0xF4**（4B float，`imu_rate_hz`，100Hz 快环发送），GCS
`decode_imu_health` 解码并写入 CSV 列 `imu_rate_hz`；用 `tvc record` 无 DBG
测量：

| 版本 | imu_rate_hz n | min | max | mean | std |
|---|---|---|---|---|---|
| 默认轮询 | 443 | 99.1 | 1760.2 | **1429.6** | 263.2 |
| FIFO 2包 | 538 | 205.6 | 3530.8 | **2107.1** | 571.3 |

两版静态 `vel=0`、姿态稳定；FIFO2 平均接近2k但抖动大（std571），不是稳定
2 kHz。结论：FIFO2 可作候选但未达“稳定2k”；默认已回退轮询版，板上保留
0xF4 遥测用于后续无 DBG 测量。

## 11. TIM8 时基 6.4→12.8 kHz A/B（2026-11-04）

`BFS_SCHED_TICK_HZ=12800` 独立 env，非 DBG 0xF4 遥测实测：

| 时基 | mean | std | min | max |
|---|---|---|---|---|
| 6.4 kHz | 1429.6 | 263.2 | 99.1 | 1760.2 |
| 12.8 kHz | 1409.4 | 266.9 | 98.4 | 1787.5 |

**提频没有改善采样率/抖动**，说明不是 tick 粒度问题；瓶颈仍是主循环里
的 IMU 处理耗时/任务调度。实验 env 已撤销，默认 6.4 kHz。

## 12. 扩展任务推迟 A/B（2026-11-04）

在已有 ELRS/日志 deferrable 基础上，把 AnoCom/CANBus/Debug/VerticalKF 也标记
可推迟（GNC/Navigation/IMU 不推迟），非 DBG 0xF4：

| 版本 | mean | std |
|---|---|---|
| 默认 | 1429.6 | 263.2 |
| 扩展推迟 | 1416.8 | 220.1 |

抖动略降，采样率没升。说明继续调任务推迟/时基收益有限，必须拆分采样/
处理架构；实验已撤销。

## 13. Madgwick 200Hz 降频 A/B（2026-11-04）

把备份 Madgwick 降到 200Hz（IMU 增量/EKF 仍每样本），非 DBG 0xF4：
mean=1357.9 Hz、std=310.2、min93.3/max1832.6；比默认更差。
说明备份姿态不是主要成本，降频不解决问题；实验已撤销。

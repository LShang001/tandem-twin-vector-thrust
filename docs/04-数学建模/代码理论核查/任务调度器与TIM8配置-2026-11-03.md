# 任务调度器与 TIM8 实际配置（2026-11-03）

> 目的：把“定时器怎么配、任务怎么被置位、为什么会丢执行”用实测固定下来，
> 作为后续调度升级（FIFO/优先级/专用采样）的基线。

## 1. TIM8 实际配置（上板读取）

`tasks` 新增打印：

```
TIM8 clk=240000000Hz psc=1 arr=37500 tick_hz=6400
```

- TIM8 定时器时钟 **240 MHz**（APB2 定时器时钟）。
- `PSC=1`（预分频因子 1，寄存器值 0）、`ARR=37500`（周期 37501 计数）。
- 实际 tick ≈ 240e6 / 37501 = **6399.8 Hz**，与设计 6400 Hz 一致。
- 1 tick = **156.25 µs**；Q8 定点可表达 3.2 tick（2 kHz IMU）等分数周期。

## 2. 调度实现

```
TIM8 6.4 kHz ISR:
  s_timerTicks++
  for each task:
    if enabled && (now - lastRun >= interval):
      if flag: missed_count++      ← 上一拍未消费，本次到期被合并
      flag = true
      lastRun = now
      (Q8 分数周期) interval = nextInterval(...)

主循环 taskExecutor():
  for each task in 注册顺序:
    if flag: flag=false; 执行任务
```

- 无抢占、无优先级、每轮每任务最多执行一次。
- `flag` 是布尔量：**ISR 第二次到期时若 flag 仍为 true，只置 true 一次，
  这次执行永久丢失**；旧统计只有“迟到”（间隔 >1.5×名义），无法量化这种合并。
- 新增 `missed_count`（丢执行）列，直接在 `tasks` 表输出。

## 3. 上板基线（CAN/光流已关闭）

```

ICM42688    1600   1552   105   152   87   644   2829   1540   3451   16.3
DPS310      130    129    107   211   721   7727  10128   0      0      1.4
Navigation  200    200    1482  2409  3066  4998  5556    0      0      29.7

```

- IMU 窗口 7.7 s 丢执行 **3451 次 ≈ 448 次/s**；实际 1552 Hz，与
  `1600-448≈1152` 的量级关系受窗口/统计口径影响，但方向明确。
- 200 Hz 任务（Navigation/GNC 等）迟到 0、实际 200 Hz，**主环本身稳定**。
- 非 DBG 的 `imu_rate` 平均 1576–1600 Hz；`imu_rate` 是每个 Navigation 5ms 窗口的瞬时值，min≈1 kHz 表示某一帧少 3 个样本，不是整秒掉到 1 kHz；DBG `tasks`
  打印会进一步加剧丢执行，不能作为飞行速率依据。

## 4. 根因与升级优先级

1. **根因**：IMU 需要 2 kHz（500 µs）执行，主循环 pass 平均 ~644 µs；
   Navigation 单次 1.5 ms 的 pass 会吞 2–3 个 IMU 节拍。布尔 flag 无法排队。
2. **不能靠“提高任务优先级”解决**：协作式主循环里优先级只在“同一轮先跑谁”
   生效，不能打断正在执行的 Navigation；要真正解耦必须 FIFO/专用采样。
3. **不能靠“改小任务周期”解决**：名义周期已是 3.2 tick；主循环没有能力
   每 500 µs 回来一次。
4. **FIFO（推荐）**：ICM42688 2 KB FIFO，按手册 Packet 3（header+accel6+
   gyro6+temp+timestamp=16 B）批量读；任务晚 1–2 ms 仍不丢样本。
   现有 `ICM42688_FIFO` 驱动的 frame size/寄存器与手册不一致，需重写后使用。
5. **专用采样（备选）**：TIM8/DMA 在后台搬 SPI 原始样本到环形缓冲，任务只解析；
   风险和验证成本高于 FIFO。
6. **降 ODR 到 1 kHz（降级）**：能匹配当前主环，但牺牲带宽/延迟。

## 5. 定时器/ISR 还能怎么优化

- ISR 每 tick 遍历全部任务（约 20 个），6.4 kHz 下约 128k 次比较/s；当前
  CPU 不是瓶颈（ISR 估计 <2%），**不建议为此改 tick**。
- 可改为 `next_due_tick` 最小堆/有序表，减少遍历；收益小于 FIFO。
- TIM8 优先级需与 UART4/UART5 协调：当前 UART4=0、UART5=1；若 TIM8 也是 0，
  UART 不会抢占 TIM8，tick 抖动可控；改优先级必须实测 UART 丢帧与 tick 抖动。
- 统计口径必须保留：`tasks` 的 `丢执行`、`LOOP max_pass`、非 DBG `imu_rate`
  三者一起看，单看平均 Hz 会漏掉瞬态。

## 6. 结论

- TIM8 配置正确（240 MHz、PSC=1、ARR=37500、6.4 kHz），ISR 设计简单可靠。
- 当前瓶颈不是定时器精度，而是 **协作式主循环无法保证 2 kHz 服务 + 无 FIFO**；
  `丢执行` 已量化到 ~448 次/s。
- 全面升级的正确顺序：先补 FIFO 批量采样，再评估是否需要优先级/专用 DMA；
  在 FIFO 之前，不建议继续微调 tick、SPI 时钟或任务周期。


## 7. 成熟飞控一般怎么调度

| 项目 | 调度模型 | 优先级/抢占 | 典型做法 |
| --- | --- | --- | --- |
| PX4 | NuttX RTOS，POSIX 线程 + work queue | 有，抢占式 | 高频传感器/控制线程高优先级，日志/遥测低优先级；驱动与 uORB 解耦 |
| ArduPilot | ChibiOS 线程 + `AP_Scheduler` 协作任务表 | 有线程优先级；主循环内协作 | `SCHED_TASK` 固定频率表 + timer process 处理快速事件；主循环按表执行 |
| Betaflight / iNav | 裸机协作式 scheduler | 基本无任务抢占 | 固定任务表（gyro/PID/accel/…），陀螺中断/DMA 驱动；靠极快主循环和任务预算保证 |
| 本项目 | 裸机协作式 + TIM8 flag | 无抢占、无优先级 | 200 Hz 主环稳定；2 kHz IMU 靠 64 深缓冲，任务晚拍会丢样本 |

共同点不是“必须有优先级”，而是：

1. **高频/硬实时的采集（陀螺）必须与慢任务解耦**：中断/DMA/FIFO/独立线程；
2. **控制环有明确截止时间**，不能被日志/遥测/导航长计算拖过周期；
3. 优先级只在**抢占式**调度下才能解决“长任务挡住短任务”；协作式里
   “优先级”最多决定同一轮先跑谁，不能打断正在执行的任务。

## 8. 本项目要不要上优先级

- **只给现有协作调度器加优先级数字，不解决问题**：Navigation 一次 1.5 ms
  仍在主循环里跑，IMU 的 500 µs 节拍照样被吞。
- **优先做 FIFO/专用采集**：保持现有 200 Hz 协作主环，用 ICM42688 2 KB FIFO
  吸收任务抖动；这是改动最小、风险最低的路径。
- **若以后要求硬实时多速率**（例如 400–1000 Hz 控制、多传感器并发），再考虑
  混合架构：
  - 高优先级：IMU SPI DMA/中断采集（只搬数据，不做重计算）；
  - 中优先级：控制/导航；
  - 低优先级：遥测、日志、调试；
  - 共享数据用无锁环形缓冲/双缓冲，避免优先级反转。
- 直接换 FreeRTOS 不是免费升级：要重新做栈、优先级、互斥、看门狗、
  失效保护和时序验证；当前 200 Hz 控制稳定，不建议为 IMU 单点问题整体换 RTOS。

结论：**成熟飞控普遍用“优先级/抢占 + 高频采集解耦”，但是否需要优先级取决于
硬截止时间和阻塞；本项目当前应先用 FIFO 解耦 IMU，优先级/RTOS 留到控制率
提升或多传感器并发时再做。**

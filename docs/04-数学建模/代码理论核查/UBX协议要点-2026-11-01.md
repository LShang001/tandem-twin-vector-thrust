## 1. UBX 帧结构

### 1.1 字节级布局

手册 §3.2 UBX frame structure（第 53 页）原文要点：

- 帧以 2 字节前导开始，两个同步字符 `0xb5` 和 `0x62`；
- 随后 1 字节 message class，1 字节 message ID；
- 随后 2 字节 length：**仅表示 payload 字节数**，不含前导、class、ID、length 和校验字段；
  该字段是 **小端无符号 16 位整数（"U2"）**；
- payload 长度可变（= length）；
- 最后两个 1 字节字段 CK_A、CK_B。

因此一帧的完整布局与偏移为：

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 1 | 同步字 1 | `0xB5` |
| 1 | 1 | 同步字 2 | `0x62` |
| 2 | 1 | class | 消息大类（`0x01`=NAV，`0x05`=ACK，`0x06`=CFG…） |
| 3 | 1 | id | 消息号 |
| 4 | 2 | length (U2, LE) | **仅 payload 长度**，0…65535 |
| 6 | length | payload | 二进制任意字节 |
| 6+length | 1 | CK_A | 8-bit Fletcher 低字节 |
| 7+length | 1 | CK_B | 8-bit Fletcher 高字节 |

> **关键推论（用于 §2 重同步）**：length 只算 payload，且 payload 是**任意二进制**。
> 因此 `0xB5 0x62` 完全可能作为普通数据出现在 payload 内部——解析器必须能区分
> "真帧头"与"payload 里的假帧头"，这就是重同步策略存在的根本原因。

### 1.2 长度上限

协议层 length 是 U2，理论最大 payload 为 65535 字节。本库把上限压到
`UBX_MAX_PAYLOAD_ = 1024`（`ubx.h:414`），这是**库的裁剪选择，不是协议限制**。

对照本库需要处理的消息，1024 足够：

| 消息 | 长度公式（手册） | 实测/推算最大值 | 是否超 1024 |
| --- | --- | --- | --- |
| NAV-PVT | 固定 92（§3.15.13.1，第 145 页） | 92 | 否 |
| NAV-EOE | 固定 4（§3.15.4.1，第 138 页） | 4 | 否 |
| NAV-HPPOSLLH | 固定 36（§3.15.7.1，第 140 页） | 36 | 否 |
| NAV-HPPOSECEF | 固定 28（§3.15.6.1，第 139 页） | 28 | 否 |
| NAV-RELPOSNED | 固定 64（§3.15.14.1，第 148 页） | 64 | 否 |
| NAV-TIMEGPS | 固定 16（§3.15.25.1，第 159 页） | 16 | 否 |
| NAV-SAT | `8 + numSvs·12`（§3.15.16.1，第 150 页） | 60 SV → 728 | 否 |
| **RXM-RAWX** | `16 + numMeas·32`（§3.17.6，第 188 页） | 60 测量 → 1936 | **是** |
| **CFG-VALGET** | 最多 64 个键值对（§3.10.25，第 95 页） | 可 > 1024 | **是** |

结论：当前"只解析 NAV 类"的用法下 1024 富裕；只有将来接 RAWX（原始观测做
PPP/RTK 自解算）或把配置回读并进本解析器时才会撞上限。那时需要提高
`UBX_MAX_PAYLOAD_`（RAM 代价：`UbxMsg` 里是定长数组，`ubx.h:551-557`）或改为
"头部先解析、payload 流式回调"。

### 1.3 校验和覆盖范围

手册 §3.4 UBX checksum（第 56 页）原文：

> The checksum is calculated over the message, **starting and including the class
> field up until, but excluding, the checksum fields**.
>
> The checksum algorithm used is the 8-bit Fletcher algorithm, which is used in the
> TCP standard (RFC 1145) […] CK_A and CK_B values are 8-bit unsigned integers, only!
> If implementing with larger-sized integer values, make sure to mask both CK_A and
> CK_B with the value `0xff` after both operations in the loop.

即校验范围为 **class + id + length(2B) + payload**，共 `4 + length` 字节，**不含**两个
同步字，**不含** CK_A/CK_B 自身。

算法（手册伪码）：

```
CK_A = 0, CK_B = 0
for I = 0 .. N-1:
    CK_A = CK_A + Buffer[I]
    CK_B = CK_B + CK_A
```

本库实现对照：

- `Checksum::Compute()`（`ubx.h:517-530`）逐字节 `sum0_ += data[i]; sum1_ += sum0_;`，
  累加器是 `uint8_t`，天然按 256 回绕，等价于手册要求的 `& 0xFF` 掩码。**算法正确**。
- 调用点 `ubx.cpp:1221-1223`：`chksum_rx_.Compute(reinterpret_cast<const uint8_t*>(&rx_msg_), rx_msg_.len + UBX_CHK_OFFSET_)`。
  这里依赖 `UbxMsg` 的内存布局必须恰好是 `cls, id, len(2B), payload[]` 且无填充
  （`ubx.h:551-557` 已加 `UBX_PACKED`；四个字段自然对齐，即使无 `packed` 也不会插入填充）。
  `UBX_CHK_OFFSET_ = 6 - 2 = 4`（`ubx.h:422`），正好是"从 cls 起、跳过同步字"的偏移。
  **起止范围与手册一致**。
- 比较侧 `ubx.cpp:1226`：`chk_cmp_rx_ == (c_ << 8 | chk_rx_)`，即"收到的 CK_B 在高字节、
  先到的 CK_A 在低字节"，与 `Compute` 返回值 `sum1<<8|sum0` 对应。**字节序正确**。

> 一个隐患（推断，非手册结论）：上述正确性**依赖 `UbxMsg` 的内存布局**。
> `ubx.h:422` 的注释把 `UBX_CHK_OFFSET_` 定义成"头长减同步字长"，语义上是对的，
> 但若将来有人把 `UbxMsg` 改成非 packed 且插入填充（例如加一个 `uint8_t version`
> 或把 `len` 改 `uint32_t`），CRC 会静默算错。建议改为对三个字段分别
> `Update(&cls,1); Update(&id,1); Update(&len,2); Update(payload,len)`，
> 从"布局依赖"变成"字段显式拼接"。

## 2. 同步与重同步

### 2.1 现有状态机

`Ubx::ProcessUbxByte()`（`ubx.cpp:1157-1237`）是逐字节、跨调用持久的状态机，
用 `parser_state_`（`ubx.h:425`）表示"已收帧内位置"，分 8 段：

| `parser_state_` | 处理 | 代码（@04:26 快照） |
| --- | --- | --- |
| 0…1 | 匹配同步字 `0xB5`、`0x62` | 1161–1170 |
| 2 | 收 class | 1176–1179 |
| 3 | 收 id | 1181–1184 |
| 4 | 收 length 低字节（LE） | 1186–1189 |
| 5 | 收 length 高字节并合成 `rx_msg_.len` | 1193–1202 |
| 6 … 5+len | 收 payload | 1205–1208 |
| 6+len | 收 CK_A | 1211–1214 |
| 7+len | 收 CK_B，算校验并比对 | 1220–1236 |

`parser_state_` 不随函数返回清零，所以一帧可以拆到多次 `Pump()` 调用里完成
（`ubx.cpp:1153-1156` 的注释亦是此意）。这个设计本身是对的，也是 `Pump(max_bytes)`
字节预算能工作的前提。

### 2.2 缺陷 1：同步段回退会吞掉下一帧（✅ 已于本轮回修复）

原实现（`ubx.cpp:1161` 附近，快照前的状态）：

```cpp
if (parser_state_ < sizeof(UBX_HEADER_)) {      // sizeof == 2，即 state 0 或 1
  if (c_ == UBX_HEADER_[parser_state_]) {
    parser_state_++;
  } else {
    parser_state_ = 0;                          // ← 问题所在
  }
}
```

流 `… B5 B5 62 01 07 92 …` 的行为：

| 输入字节 | 进入前 state | 期望 | 结果 | 新 state（旧实现） |
| --- | --- | --- | --- | --- |
| `B5` | 0 | `B5` | 命中 | 1 |
| `B5` | 1 | `62` | 失配 | **0** |
| `62` | 0 | `B5` | 失配 | 0 |
| `01` | 0 | `B5` | 失配 | 0 |

于是第二个 `B5 62`（它其实是一个合法帧头）被"吃掉"，整帧丢失。
这类序列在真实链路上有明确来源：**上一帧末尾丢字节导致状态机停在同步段**、
**上电瞬间的线路噪声**、以及**两个接收机/两种协议交替时前一段残尾**。

**当前实现（已修复）** —— `Ubx::ProcessUbxByte()`，`ubx.cpp:1161-1173`：

```cpp
if (parser_state_ < sizeof(UBX_HEADER_)) {
  if (c_ == UBX_HEADER_[parser_state_]) {
    parser_state_++;
  } else {
    // 重同步：当前字节若是同步字首字节 0xB5，把它当作新帧头起点，
    // 否则回到空闲。处理 "B5 B5 62 ..." 这类连续同步字场景。
    parser_state_ = (c_ == UBX_HEADER_[0]) ? 1U : 0U;
  }
}
```

因为 `UBX_HEADER_[0]` 与 `UBX_HEADER_[1]` 不相等（`0xB5 ≠ 0x62`），不存在
"部分匹配前缀"的更复杂情况，这一行就够了。若将来同步字改成有自重叠的模式，
才需要完整的 KMP 失配函数。

**回归用例**（建议进宿主机测试）：注入 `B5 B5 62 01 07 5C …`（合法 PVT 帧前面多一个
`B5`），断言 `valid_msg_count_ == 1`、`nav_pvt_count_ == 1`。旧实现该断言必失败。

### 2.3 缺陷 2：坏 CRC 后整段丢弃，可能吞掉帧头（🟡 部分缓解，仍建议做重扫）

当前实现（`ubx.cpp:1220-1236`，节选）：

```cpp
chk_cmp_rx_ = chksum_rx_.Compute(...);
parser_state_ = 0;                       // 无论成败都复位
if (chk_cmp_rx_ == (c_ << 8 | chk_rx_)) { valid_msg_count_++; return true; }
checksum_fail_count_++;
// 坏帧的 CK_B 也可能恰是下一帧同步字首字节 0xB5，保留重同步机会。
parser_state_ = (c_ == UBX_HEADER_[0]) ? 1U : 0U;   // ← 本轮回新增
```

新增的这一行已经消除了最常见的一种吞帧：**坏帧的 CK_B 恰好是下一帧的 `0xB5`**。
但更一般的情况仍未覆盖：

问题在于：如果这个"帧"其实是**payload 内部的假同步字**（§1.1 的推论），那么被当作
`len`、`payload` 消费掉的那 `length+4` 个字节里，**可能正含着下一帧的真帧头**。
这些字节已经过去了，不会再被检视，于是真帧丢失（表现为 `checksum_fail_count_` 一次、
随后 `eoe_without_pvt_count_` 或 `nav_pvt_count`/`nav_eoe_count` 不匹配上升）。

完整改进方案（只在失败路径付费，不影响正常路径）：

```
// 候选帧的完整字节 = {B5, 62, cls, id, lenL, lenH, payload...}，长度 n = len + 6
// 从索引 1 开始找下一个 B5 62；命中则把命中的 62 之后（即下一字节）重新喂给状态机
for (i = 1; i + 1 < n; ++i) {
    if (cand[i] == 0xB5 && cand[i+1] == 0x62) { replay(cand + i); break; }
}
```

其中 `cand` 的全部内容其实已经在 `rx_msg_` 里（class/id/len/payload），只是缺两个同步字，
可以在重扫时按 `{0xB5,0x62, rx_msg_…}` 拼出。代价：一次 ≤1024 字节的线性扫描，
仅在 CRC 失败时发生（本库注释 `ubx.cpp:1231` 也承认"校验失败应保持为 0，非 0 多为接线/波特率问题"，
即属异常路径）。

> 更彻底的做法是"帧缓冲 + 失败后按字节滑动重解"，但那需要额外 RAM 保存原始字节；
> 上面这个"用已缓存 payload 重扫"的方案在 RAM 上零额外开销，已能消除绝大部分吞帧。

### 2.4 缺陷 3：超长 payload 的处理（🟡 部分缓解）

```cpp
// ubx.cpp:1193-1202
rx_msg_.len = static_cast<uint16_t>(c_) << 8 | len_;
parser_state_++;
if (rx_msg_.len > UBX_MAX_PAYLOAD_) {
  oversize_msg_count_++;
  parser_state_ = (c_ == UBX_HEADER_[0]) ? 1U : 0U;   // 本轮回改为保留重同步机会
}
```

越界时现在会把"当前这个 length 高字节"也当作潜在同步字检查一次，比原来的无条件
`parser_state_ = 0` 好；但仍**没有"跳过剩余 payload 再同步"的概念**：
接下来最多 1024 字节会被继续当帧头扫描（可能扫到 payload 里的假 `B5 62` 又起一帧，
再由 CRC 拦下——安全但浪费）。

建议：与 §2.3 合并处理——越界时不要立刻清零，而是**跳过剩余长度并重新同步**，
或干脆按"把当前字节喂给同步段的初始状态"处理。

### 2.5 缺陷 4：无帧内超时

`parser_state_` 跨调用保留，但没有任何"半帧悬挂超时"。若一帧中间丢了一个字节：

- 状态机继续把后续字节当 payload 吃，直到吃满 `length` 字节；
- 然后算 CRC → 必然失败 → 复位（`ubx.cpp:1224`）；
- 期间最多吞掉 `length + 2` 字节（≤1026 B）。**在 921600 下约 11 ms**，可接受。

但如果对端**停止发送**（掉电、线松、进入配置模式），状态机会永久停在半帧，
`parser_state_ != 0` 且无任何数据产出，上层只能靠"epoch 长时间不来"间接发现。
建议增加 `last_rx_byte_us_`，在 `Pump()` 入口做：

```cpp
if (parser_state_ != 0 && micros() - last_rx_byte_us_ > kFrameTimeoutUs) {
    frame_timeout_count_++; parser_state_ = 0;
}
```

### 2.6 重同步的正确性要求（小结）

1. **绝不因失配而丢弃"当前字节可能作为新帧起点"的信息**（§2.2）；
2. **CRC 失败要能在已收到的字节里找回后续帧头**（§2.3）；
3. **越界/超长时不产生二次误判**（§2.4）；
4. **半帧悬挂要有超时出口**（§2.5）；
5. 所有重同步动作都要**可计数**，否则现场无法区分"链路差"与"解析器 bug"。

## 3. 混合流：UBX 与 NMEA 0183 交替

### 3.1 物理层共存方式

同一根 UART 上同时输出 UBX 与 NMEA 是 u-blox 的标准用法（配置项
`CFG-PRT` 的 `inProtoMask/outProtoMask` 可同时置 `UBX`、`NMEA` 位，
本库 `ubx_defs.h:99-102` 已定义 `UBX_COM_PROT_UBX_ = 0x01` / `UBX_COM_PROT_NMEA_ = 0x02`）。
此时两个协议的字节流**在时间上交替，但每个帧/句自身是完整的**：
UBX 帧以 `0xB5` 开头，NMEA 句以 ASCII `$` 开头、以 `*cs\r\n` 结束
（手册 §2.9.2 的句结构行写作 `…*cs\r\n`）。

### 3.2 识别规则

- UBX 帧：首字节 `0xB5`，次字节 `0x62`；
- NMEA 句：首字节 `'$'`（0x24），ASCII 可打印字符，`'*'` 后两位十六进制校验，`\r\n` 结束；
- 两个一字符集基本不重叠（`$`=0x24，`0xB5`=181 非 ASCII），所以**在帧边界上**判别是可靠的。

不可靠的地方是：**在 UBX payload 内部**。payload 是任意二进制，可能含 `0x24`（`'$'`）、
`0x0D`/`0x0A`。因此"见到 `$` 就当 NMEA 句首"这条规则，只有在该字节**位于帧边界**时才成立。

### 3.3 EOE 与 NMEA 的时序关系（重要）

手册 §3.15.4.1 UBX-NAV-EOE（第 138 页）Comment 原文：

> This message is intended to be used as a marker to collect all navigation
> messages of an epoch. It is output **after all enabled NAV class messages
> (except UBX-NAV-HNR) and after all enabled NMEA messages**.

这条定义带来两个直接结论：

1. **EOE 是"本历元所有输出（含 NMEA）都已发完"的唯一同步点**。若上层要
   "UBX 位置 + 同历元 NMEA 原始句"配对，正确做法是**缓存 NMEA 句，收到 EOE 时一起交出**；
2. **NMEA 句没有 iTOW 字段**（只有 UTC 的 `hhmmss.ss`，见 §6.5），所以 NMEA 与 UBX 之间
   只能靠"落在哪个 EOE 区间"对齐，不能靠时间戳精确配对。

### 3.4 本库现状

`Pump()` 里两个解析器**对每个字节并行运行**，没有互斥：

```cpp
// ubx.cpp:266-280（现状）
if (ubx_enabled)  { if (ProcessUbxByte(b)) { if (HandleValidMessage(true)) {...} } }
if (nmea_enabled) { nmeaProcessByte(b); }
```

`nmeaProcessByte()`（`ubx.cpp:523-560`）的规则是：不在句中时只有 `'$'` 能起句；
在句中时 `\r`/`\n` 结束、`'$'` 重新同步、超过 95 字节丢弃（`ubx.cpp:553-558`）。

由此产生的实际风险（按严重度）：

| 风险 | 说明 | 后果 |
| --- | --- | --- |
| UBX payload 里的 `0x24` 误起 NMEA 句 | 极小概率下后续字节凑成 `\r`/`\n` 结束，形成一句垃圾 | `nmea_bad_checksum_count_` 噪声；极端情况下若垃圾句恰好校验通过且字段合法，会污染 NMEA 快照 |
| UBX payload 里的 `0x24` 让 `nmea_in_sentence_=true` 并吃掉 96 字节 | 若 96 字节内没有 `\r`/`\n`/`$` | 触发 `nmea_overflow_count_`，期间真 NMEA 句被丢 |
| 两套计数混在一起 | `nmea_sentence_count_` 统计的是"所有进入解析器的句子" | 现场难以判断"是接收机发得多，还是解析器误判多" |

**建议的单状态机分派**（与手册定义一致，且改动最小）：

```
// 帧边界状态（idle）：
//   0xB5 -> 进入 UBX 帧解析（后续按 ProcessUbxByte 推进）
//   '$'  -> 进入 NMEA 句收集（直到 '\r'/'\n' 或超长）
//   其它 -> 丢弃（计入 idle_noise_count_）
// 帧内状态：只喂当前协议的状态机，另一个解析器不参与
```

这条规则的实质是：**NMEA 只在 UBX 状态机空闲（`parser_state_ == 0`）时收字节**。
因为 NMEA 是 ASCII，不含 `0xB5`，所以 UBX 状态机在 NMEA 句期间始终为 0，
两者不会互相打断。改动只需在 `ubx.cpp:277-280` 加一个 `if (parser_state_ == 0)` 的条件，
并把"当前是否正在 NMEA 句中"作为另一个互斥条件（避免 NMEA 句跨到 UBX 帧里）。

### 3.5 另一个现状差异：`Read()` 路径不喂 NMEA

`Read()`（`ubx.cpp:213-233`）只调 `ParseMsg()`→`HandleValidMessage(false)`，
**完全不调用 `nmeaProcessByte`，也不入队**。而 `Pump()` 两条都做。
即：`Read()` 只在 `kUbx` 模式下自洽；`kAuto`/`kNmea` 下用 `Read()` 拿不到任何 NMEA 数据。
固件当前只用 `Pump()`（`main.cpp:205/543`），所以未暴露，但头文件里
"两套独立用法不要混用"（`ubx.h:141`）的提醒并不能阻止误用。建议在 `Read()` 里
同样喂 NMEA，或加编译期/运行期断言。

### 4.2 NAV-EOE（0x01 0x61）—— 历元结束语义

手册 §3.15.4.1（第 138 页），固定长度 4，payload 只有 `iTOW`（U4，ms）。

语义（原文见 §3.3 已引）：**本历元所有已启用的 NAV 类消息（除 NAV-HNR）与所有已启用的
NMEA 消息都发完之后**才输出。因此它天然是"历元栅栏"。

本库用法（`ubx.cpp:410-455`）：

1. 收到 EOE 即视为"本历元结束"；
2. 若本历元**没收到过 NAV-PVT**（`pvt_ready_this_epoch_ == false`），记
   `eoe_without_pvt_count_` 并直接丢弃（`ubx.cpp:419-423`）——不会推送半截历元，正确；
3. 比对 `PVT.iTOW == EOE.iTOW`，不等则记 `tow_mismatch_count_` 并丢弃（`ubx.cpp:433-437`）；
4. 通过后 `ProcessNavData()` 换算 → `MakeEpoch()` → `PushEpoch()`（仅 `queue_output=true` 的 `Pump` 路径）。

> **注意时序陷阱**：因为 EOE 在 NMEA 之后，若上层把"收到 EOE"当作"立即返回给控制环"
> 的信号（`Read()` 就是这样，`ubx.cpp:213-233`），那么从"本历元第一条 NAV 消息到达"
> 到"EOE 到达"之间的全部耗时都算进了延迟。混合输出 NMEA 时这个窗口会明显变长。
> 这也是 §6.3 "时间戳应取 EOE 时刻"的理由之一。

## 5. 性能

### 5.1 当前链路的真实带宽占用（先算账）

本项目的实际配置（`TandemVec_FCS/src/ubx_config.cpp:431-440`）只启用两条消息：

```cpp
_cfg_msg(serial, 0x01, 0x07, 1);   // NAV-PVT
_cfg_msg(serial, 0x01, 0x61, 1);   // NAV-EOE
```

配合 `main.cpp:230-236` 的目标波特率 **921600**、导航速率 **100 ms（10 Hz）**：

| 项 | 字节/历元 | 10 Hz 下 B/s | 921600 8N1（≈92160 B/s）占比 |
| --- | --- | --- | --- |
| NAV-PVT | 92 + 8 = 100 | 1000 | 1.09% |
| NAV-EOE | 4 + 8 = 12 | 120 | 0.13% |
| 合计 | 112 | **1120** | **≈1.22%** |

即使把 F9P 常用的 HPPOSLLH(44)+HPPOSECEF(36)+RELPOSNED(72)+TIMEGPS(24)+NAV-SAT(30 星
376) 全开，也只再加 ~552 B/历元（664 B/历元 → 约 6.64 kB/s ≈ **7.2%**）。

**结论：逐字节解析当前不是瓶颈。** 1.1 kB/s 意味着每毫秒才 1.1 个字节进入状态机，
200 Hz 主循环每次 `Pump()`（预算 512 B，`state_data.cpp:573`）绝大多数时候只读到
十几到几十字节。

### 5.2 逐字节 vs 批量读/DMA

本库三处逐字节读：`Read()`（`ubx.cpp:220-231`）、`Pump()`（`ubx.cpp:255-264`）、
`ParseMsg()`（`ubx.cpp:1135-1148`）。每字节的成本是：

1. `bus_->available()` —— 一次虚调用（Arduino `HardwareSerial` 继承 `Stream`）；
2. `bus_->read()` —— 又一次虚调用 + 内部临界区/锁（ESP32 Arduino 的 `read()` 会取
   UART 互斥量）；
3. `ProcessUbxByte()` 里的分支链（8 个 `else if`）与一次 `rx_msg_.payload[]` 写。

粗估每字节几百 ns 到 µs 量级。按 1120 B/s 折算，**总 CPU 占比 < 0.1%**，可忽略。

批量方案（仅在未来加负载时值得做）：

- Arduino 层：`bus_->read(buf, n)` / `readBytes()` 一次拿一批，再在本地数组上跑状态机；
  `available()` 也只需每次 `Pump()` 调一次。
- ESP32 特定：`uart_driver_install()` + `uart_read_bytes()`（带超时的阻塞读，可放在
  低优先级任务里），或 DMA 半满中断。这会把"每字节 2 次虚调用"降到"每批 2 次"。
- 代价：需要一个 `uint8_t buf[N]`（N=128/256 即可覆盖 10 ms 的数据量），RAM 开销极小。

### 5.3 payload 上限与批量解析

如 §1.2 所述，1024 字节上限对 NAV 类够用。若做"批量解析"，可顺带把上限语义改清楚：
现在的处理是"越界即丢整帧"（`ubx.cpp:1198-1202`），更稳的做法是
"仍按 length 收完再丢"——否则残留在 buffer 里的字节会污染下一次同步（见 §2.4）。

### 5.4 校验和优化：能不能查表？

这是最容易做错方向的一项，先把数学说清。

8-bit Fletcher 是**纯加法**递推：`A_i = A_{i-1} + b_i`，`B_i = B_{i-1} + A_i`（模 256）。
因为全是加法，模 256 与加法可交换（同态），所以：

- 可以用 `uint32_t` 累加、**只在结束时 `& 0xFF`**，结果与逐字节 `uint8_t` 累加**完全等价**
  （当前实现用 `uint8_t` 累加器，靠 C++ 无符号回绕自动等价，`ubx.h:524-529`）；
- 32 位累加器在 Cortex-M/RISC-V 上少一次截断依赖，且能 4 字节展开
  （`a+=d0; b+=a; a+=d1; b+=a; …`），流水线友好；
- 也等价于闭式（`j` 从 0 起）：`CK_A = Σb_j mod 256`，`CK_B = Σ (n−j)·b_j mod 256`。

**关于查表**：CRC-32 那种 256 项查表依赖"移位 + 异或"的 GF(2) 结构，Fletcher 没有这种结构，
**不存在等价的单字节查表法**。唯一能"查表"的是上面的加权形式——若预先知道总长 `n`，
可以按 4 字节一组查"权重表"，但权重随位置变化，构造与缓存成本高于直接累加，
**收益为负**。所以：

| 优化 | 是否值得 | 预期收益 |
| --- | --- | --- |
| 收字节时**增量累加**，省掉收齐后的二次遍历 | ✅ 强烈建议 | 直接省掉 `ubx.cpp:1221-1223` 的整段二次扫描（相当于负载减半） |
| `uint32_t` 累加 + 末尾掩码 + 4 字节展开 | ✅ 建议 | 单次遍历再快 1.5–2×（对整体影响很小） |
| 256 项查表 | ❌ 不适用 | Fletcher 无此等价形式 |
| 让 DMA 完成后再校验（一次线性扫） | ✅ 大批量时 | 与"增量累加"二选一即可 |

### 5.5 虚函数与动态分配

- **动态分配：无。** 全库定长：`epoch_queue_[kEpochQueueCapacity]`（`ubx.h:87/502`，
  容量 4）、`rx_msg_.payload[UBX_MAX_PAYLOAD_]`（`ubx.h:556`）、`nmea_sentence_[96]`
  （`ubx.h:374-375`）。`UbxEpoch` 是带默认初始化器的聚合体，`PushEpoch`/`PopEpoch` 都是
  值拷贝。这一点符合飞控"运行期不分配"的要求，**应保持**。
- **逐字节间接调用：两处。**
  1. `bus_->read()` / `bus_->available()` 是虚调用（Arduino 框架固有，无法避免，
     只能靠 §5.2 的批量读摊薄）；
  2. `byte_tap_fn_`（`ubx.cpp:281-284`）是**函数指针**（`ubx.h:162`），每字节一次可空判调用。
     它不是虚函数，开销约 2–3 个周期 + 分支，可忽略；若在意，可把 tap 从"每字节"改成
     "每批"回调。
- **一次 memcpy/历元**：`HandleValidMessage` 对每条消息 memcpy 一次（92 B 最大），
  `PushEpoch` 再拷一次 `UbxEpoch`（约 90 B），`PopEpoch` 再拷一次。10 Hz 下总拷贝
  <2 kB/s，**无需优化**。

### 5.6 性能结论

> 以当前 10 Hz + 921600 + 仅 PVT/EOE 的配置，**解析器 CPU 与带宽都不是瓶颈**（<0.1% CPU、
> 1.2% 链路）。性能优化的正确顺序是：
> ① 省掉 CRC 二次遍历（改增量累加，几乎零风险）；
> ② 批量读（未来加 RAWX/更高率时再做）；
> ③ 不要引入查表 Fletcher（无收益）。
> **把精力放在 §2 的同步缺陷与 §4.7 的 iTOW 校验上，那才是真正会出错数据的地方。**

## 6. 可靠性

### 6.1 超时

| 层级 | 现状 | 建议 |
| --- | --- | --- |
| 链路探测 | `BeginConfigured()` 最多轮询 `COMM_TIMEOUT_TRIES_=1000` × `COMM_TIMEOUT_DELAY_MS_=10` = **10 s**（`ubx.h:368-369`，`ubx.cpp:197-211`） | 合理 |
| 帧内（半帧悬挂） | **无超时**（§2.5） | 加 `last_rx_byte_us_` + 50 ms 帧内超时 |
| 历元（EOE 缺失） | 无主动超时；靠上层"epoch 不来"间接发现 | 库内可提供 `last_epoch_us()`，上层算 age（固件已有 `latest_epoch_receive_time_us_`，`ubx.cpp:500`） |
| NMEA 快照 | `nmea_fix_timeout_ms_` 默认 **3000 ms**（`ubx.h:378`，判定见 `ubx.cpp:776-779`） | 对 1 Hz GGA 合理 |

### 6.2 丢字节 / 串口溢出

- **丢字节**：由 §2.2 的同步回退缺陷放大（一丢就可能连丢一帧）。此外，若在 payload 中间
  丢字节，状态机会把后续字节错位当成 payload，直到 CRC 失败——**只损失当前帧**，
  这是状态机设计的优点。
- **串口溢出（接收机侧 MON-RXBUF / 主机 UART FIFO overrun）**：本库**无法感知**。
  `rx_byte_count_`（`ubx.cpp:265`）只统计"读到的字节"，读不到被硬件丢弃的字节。
  两个可用间接信号：
  1. `checksum_fail_count_ > 0` —— 稳态应为 0（`ubx.cpp:1231` 注释也是这个意思）；
  2. `nav_pvt_count` / `nav_eoe_count` 的比值偏离 1 —— 说明历元被截断。
  **建议**：若接收机侧可用，周期读取 `UBX-MON-COMMS`（`0x0A 0x36`，手册 §3.14.1，
  第 126 页，`8 + nPorts·40`）。其每个端口的 40 字节组里就有诊断所需的三项：
  `rxPending`（接收缓冲中待处理字节数）、`rxUsage`（上次 sysmon 周期内接收缓冲最大占用率 %）、
  `rxPeakUsage`（历史峰值 %），另有 `txErrors` 位掩码（bit0 mem / bit1 alloc）。
  把 `rxPending` 峰值与 `rxPeakUsage` 作为"主机来不及读"的直接证据——这是区分
  "接收机发得太快"与"MCU 读得太慢"的唯一可靠指标。
  > 注：老消息 `UBX-MON-RXBUF`（`0x0A 0x07`，§3.14.10，第 133 页）在**本协议版本已废弃**，
  > 手册原文 "This message is deprecated in this protocol version. Use UBX-MON-COMMS instead."，
  > 新代码请直接用 MON-COMMS。
- **主机侧溢出**：`Pump(GNSS_PUMP_MAX_BYTES=512)` 的单次预算（`state_data.cpp:573`）
  是为了避免 backlog 拖爆主循环；若主循环某拍被阻塞 >（UART RX FIFO 深度/字节率），
  硬件 FIFO 就会溢出。512 B 预算对应 921600 下约 5.5 ms 的数据量，若 UART FIFO 只有
  128–256 B，则**预算大于 FIFO 反而没意义**——真正要保证的是"主循环间隔 < FIFO 深度/字节率"。
  建议在文档里记下所选 UART 的 RX FIFO 深度，并与实测主循环间隔对照。

### 6.3 时间戳：tow 对齐与 `receive_time_us` 语义

一条 GNSS 观测的时间有四个层次：

| 层次 | 来源 | 精度 | 本库字段 |
| --- | --- | --- | --- |
| 观测时刻（GNSS 时标） | `PVT.iTOW`（ms） | 1 ms（配合 TIMEGPS.fTOW 可到 ns） | `epoch.pvt_tow_ms`、`gps_tow_s` |
| 历元时刻（本机时标） | 收到 **EOE** 时的 `micros()` | µs | `epoch.receive_time_us` |
| 消息内时间精度 | `PVT.tAcc`（ns） | — | `t_acc_ns_` |
| NMEA 时刻 | `hhmmss.ss`（UTC） | **10 ms** | `nmea_snapshot_tow_ms_` |

**原实现的缺陷（✅ 已修复）**：`receive_time_us` 曾取 `Pump()` **调用开始**时传入的
`micros()`：

```cpp
// 修复前：ubx.cpp:247-249 与 462-463
bool Ubx::Pump(size_t max_bytes, uint32_t receive_time_us) {
    pump_receive_time_us_ = receive_time_us;     // ← 调用方在进入 Pump 前取的时刻
    ...
epoch.receive_time_us = pump_receive_time_us_;   // ← 直接搬运
```

固件调用点 `main.cpp:543`：`ubx.Pump(GNSS_PUMP_MAX_BYTES, micros())`。
若某个历元的 EOE 落在本次 Pump 的第 N 个字节，则该历元被打上的时间戳比真实到达时刻
**早 N/字节率** 秒。正常情况（每次 Pump 只有几十字节）偏差 <1 ms；但以下场景会放大：

- 主循环被长任务阻塞后一次性排空 512 B → 偏差可达 **5.5 ms**；
- 921600 下若 backlog 超过预算，跨多次 Pump 才能到达 EOE，偏差可达数十 ms。

而 `receive_time_us` 正是 `InsGnssMapEpochToLocalTime()`（`navigation_task.cpp:1759-1764`）
用来估计"这条观测在本机时基上的时刻"的输入，也就直接进 `gnss_measurement_age_s`。
当前 `BFS_NAVIGATION_GNSS_DELAY_S = 0.015f`（15 ms，见既有调研文档），**5 ms 级偏差已是同阶**。

**✅ 当前实现（已修复）**：在 EOE 帧组装完成（CRC 通过）的那一刻取时间戳：

```cpp
// ubx.cpp:430（EOE 分支，ProcessNavData 之前）
eoe_receive_time_us_ = micros();
// ubx.cpp:462-463（MakeEpoch）
epoch.receive_time_us = (eoe_receive_time_us_ != 0U) ? eoe_receive_time_us_
                                                     : pump_receive_time_us_;
```

`pump_receive_time_us_` 退化为首帧兜底（`eoe_receive_time_us_` 只在 `Reset()` 清零），
语义正确。**残留的一处不一致**：`MakeNmeaEpoch()` 用 `micros()`（`ubx.cpp:718`，即合成
时刻），而 `MakeEpoch()` 现在用 EOE 时刻——两条路径都是"到达时刻"，语义已对齐，
但 NMEA 合成时刻仍在 `TryPushNmeaEpoch()` 里取，比 EOE 晚一个 Pump 周期以内，可接受。

### 6.4 重复 iTOW 去重

职责划分是清楚的：

- **库内**：只做"同一历元内重复 PVT"计数（`ubx.cpp:334-343`，
  `pvt_duplicate_in_epoch_count_`），并做 PVT/EOE 的 iTOW 比对（`ubx.cpp:433`）。
  它**不**做跨历元去重——`PushEpoch` 不检查新 epoch 的 `pvt_tow_ms` 是否与上一帧相同。
- **固件内**：`gnssEpochPassesFullQuality()`（`navigation_task.cpp:362-367`）用
  `epoch.pvt_tow_ms == gnss_status.last_tow_ms` 拒收重复历元，并计数
  `duplicate_itow_count`；`last_tow_ms` 只在**融合成功后**更新（`navigation_task.cpp:1991`）。
  降级路径 `gnssEpochQualifiesForDowngrade()` 也做了同样的判重（`:407-410`）。

这个分工是合理的（库只管协议，策略在上层）。但有两个遗留点：

1. **`Reset()` 漏清 `pvt_duplicate_in_epoch_count_`**（声明 `ubx.h:435`、自增
   `ubx.cpp:340`、`Reset()` 的 `ubx.cpp:51-185` 里没有它）。软复位后统计不复位，
   长期运行的诊断页面会显示上一个会话的累计值。
2. **重复历元仍会占满队列**：库不做去重，重复 iTOW 的 epoch 照样进 4 深环形队列
   （`ubx.h:87`）。若接收机因配置错误重复输出同一历元，队列会被重复帧挤占，
   上层每次 Pop 都判重丢弃，表现为"有数据但融合率下降"。**建议**：在 `PushEpoch`
   里若 `epoch.pvt_tow_ms == latest_epoch_tow_ms_` 则直接丢弃并计数（改动 3 行），
   把去重下沉一层，避免污染队列。

### 6.5 NMEA 与 UBX 的时间基准不同（潜在缺陷）

- UBX 的 `iTOW` 是 **GPS 时间**的周内毫秒；
- NMEA 的时间字段是 **UTC** 的 `hhmmss.ss`（手册多处字段说明写作 "UTC time"，
  例如 `$PUBX,00` 的 `time` 字段，§2.9.2.2 第 48 页；NMEA 例句形如 `hhmmss.ss`，
  即**只有两位小数 → 10 ms 量化**）。

两者相差 **GPS−UTC 闰秒**（当前 18 s，`NAV-TIMEGPS.leapS` 可读）。

本库 `MakeNmeaEpoch()`（`ubx.cpp:716-719`）把 UTC 时刻直接当"伪 tow"填进
`epoch.pvt_tow_ms` 和 `epoch.gps_tow_s`：

```cpp
epoch.pvt_tow_ms = nmea_snapshot_tow_ms_;                       // 实为 UTC 时刻
epoch.gps_tow_s  = static_cast<double>(nmea_snapshot_tow_ms_) * 1e-3;  // 实为 UTC 周内秒
```

在 `kAuto` 模式下，UBX epoch 与 NMEA epoch 进**同一个队列**，于是队列里的
`pvt_tow_ms` 序列会在"GPS 时基"和"UTC 时基"之间跳变 18 s。
当前固件只用 `pvt_tow_ms` 做**相等判重**（`navigation_task.cpp:362`）和**诊断显示**
（`last_epoch_tow_ms`），没有跨源做差值，所以**尚未引发错误**；
`gps_tow_s` 在 `TandemVec_FCS/src` 内没有被任何代码消费（本库外无引用）。
但这属于"埋着的地雷"：任何人一旦用 `gps_tow_s`/`pvt_tow_ms` 做时序对齐
（例如插值、PPS 对齐、多源时间融合），就会整体偏 18 s。

**建议**：① `MakeNmeaEpoch` 里明确命名/注释为"UTC 伪 tow"，或在合成时加
`leapS` 换算到 GPS 时基；② 给 `UbxEpoch` 增加 `bool time_base_is_gps`，
让上层能判别；③ 在文档/注释里禁止跨源比较 `tow`。

## 7. 通用性：不同 u-blox 系列、PROTVER、未知消息

### 7.1 帧层是跨系列稳定的

`§3.2`（第 53 页）与 `§3.4`（第 56 页）描述的是 **UBX 协议本身**：同步字、class/id、
U16 小端长度、Fletcher 校验、校验范围"class 起、不含 CK"。这些在所有支持 UBX 的
u-blox 产品上一致（M8/M9/F9 都适用）。**因此 §1 的帧解析逻辑本身不需要按系列分支。**

### 7.2 差异在"消息层"，且差异被手册显式标注为"依赖协议版本"

手册里能直接读到的版本依赖有三类：

| 类型 | 例子（本手册原文） | 对本库的影响 |
| --- | --- | --- |
| 字段在某些版本**不支持** | NAV-PVT `flags2.confirmedAvai`："only supported in Protocol Versions 19.00, 19.10, 20.10, 20.20, 20.30, 22.00, 23.00, 23.01, 27 and 28"（§3.15.13.1，第 146–147 页） | `ubx.cpp:894` 的与门 → 见 §7.3 |
| 字段在旧版本**不支持** | NAV-PVT `flags.carrSoln`："not supported for protocol versions less than 20.00"（§3.15.13.1，第 146 页） | `ubx.cpp:848` 的 `carrSoln` 在旧版本恒 0 → 只会退化成 `FIX_3D`，不会错算 |
| 消息带**版本号** | NAV-HPPOSLLH/HPPOSECEF `version=0x00`；NAV-SAT `version=0x01`；NAV-RELPOSNED `version=0x01`（各自章节） | 本库**从不检查 version 字段**，只按长度精确匹配 |

固件版本与协议版本的对应关系，手册 §1.2（第 16 页）给了一行示例表：

| Product firmware version | Base firmware version | Protocol version |
| --- | --- | --- |
| HPG 1.30 | EXT CORE 1.00 (9acf11) | **27.30** |

即本仓库手册对应的接收机固件族是 **HPG 1.30 / PROTVER 27.30**。

> ⚠ **本文的核实边界**：M8/M9 各自的具体 PROTVER 数值**不在**本仓库这份 F9 HPG 手册里，
> 我没有读到权威来源，因此不在本文给出具体数字。需要时请查对应产品的
> Interface Description，或**直接从接收机读**（下一节）。

### 7.3 建议：运行时读 PROTVER，而不是编译期假定

手册 §1.2 说明 `UBX-MON-VER` 的返回里带 `PROTVER=<数字>`（boot screen 与
`UBX-MON-VER` 都提供）。本库当前**完全没有读 PROTVER**，也没有利用
`payload.version`，所以无法对"版本相关字段"做降级。

**推荐做法**（按成本从低到高）：

1. **最低成本**：把 §4.1 的"六位与门"改成"三位必要条件 + 三位可选加强"：
   `validDate && validTime && fullyResolved` 为必要条件；
   `confirmedAvai/Date/Time` 仅在"接收机报告支持"时才参与。这样换任何机型都不会
   "UTC 时间恒为 0"。
2. **中等成本**：上电后发一次 `UBX-MON-VER`（`0x0A 0x04`，手册 §3.14.15，第 136 页），
   解析 `PROTVER=` 扩展字段，存 `protver_`，在需要版本分支的地方用它（例如
   `carrSoln` 只在 ≥20.00 时读）。
3. **不改代码也能做的运维措施**：把接收机型号/PROTVER 写进配置与日志
   （固件已经有 `ubxcfg` 命令体系与 `UBXCFG` 打印，扩展一行即可）。

### 7.4 消息版本号的宽容处理

本库对带 `version` 字段的消息（HPPOSLLH/HPPOSECEF/RELPOSNED/SVIN/NAV-SAT）
**一律不检查 version**，只做 `len` 精确比对：

```cpp
// ubx.cpp:403（RELPOSNED 为例）
if (rx_msg_.len == ubx_nav_rel_pos_ned_.len) { memcpy(...); rel_pos_data_ = true; }
```

评价：**行为是正确的保守策略**——长度不匹配就整帧丢弃，绝不会把新版本报文的字节
按旧布局错读（这比"强行按版本号解析"安全得多）。不足之处是**不可观测**：
现场无法知道"到底是因为版本不对被丢了，还是根本没发"。

**建议**：在 `len` 不匹配的分支里加计数（每条消息一个 `len_mismatch_count`，
或者一个共享的 `nav_len_mismatch_count_` 加 `last_msg_cls_/id_/len_` 留痕）。
已有的 `last_msg_cls_/id_/len_`（`ubx.cpp:315-317`）正是为此准备的，只差一个计数器。

### 7.5 未知 class / id 的宽容处理

现状：

- 非 NAV 类：`ubx.cpp:319-322` 直接 `return false`，只更新 `last_msg_*`；
- NAV 类内的未知 id：`ubx.cpp:447-453` 的 `default` 静默忽略；
- 但**任何** class/id 的帧都必须先通过 CRC（`ubx.cpp:1226`）——这是好事，
  意味着未知帧也会被完整校验，不会污染状态机；
- `UBX_MAX_PAYLOAD_=1024` 之外的未知大帧会被丢（§2.4）。

**评价**：默认行为符合"宽容处理、不影响已知消息"的要求，而且 CRC 先行保证了
"垃圾帧不会被当成好消息"。**缺的是可观测性**：固件诊断页拿到了
`valid_msg_count_`、`checksum_fail_count_`、`oversize_msg_count_`，却不知道
"接收机到底在发哪些我们不认识的消息"——而这恰恰是判断"接收机是不是被配错了"
（比如误开了 NMEA+UBX 双输出、或开着 RAWX 把串口塞满）的第一手证据。

**建议**：加一个 8 项链式的小直方图（`struct {uint16_t cls_id; uint16_t count;} unknown_[8];`
+ 溢出计数），记录 `(cls<<8)|id` 的前 8 个高频未知消息。RAM 代价 32 B，
诊断价值很高。另外建议对 `UBX_INF_*`（0x04，信息/调试文本）单独计数——
它是接收机在"报怨"（比如配置被拒）的唯一渠道。

## 9. 结论与"当前配置下其实没问题"的部分

为避免读者误以为整套解析器都不可用，明确区分**已核对正确的部分**：

**正确、无需改动的部分**

- UBX 帧结构解析（同步字/class/id/LE 长度/payload 边界）与 §3.2 一致；
- Fletcher 校验的算法、覆盖范围、CK_A/CK_B 字节序均与 §3.4 一致（§1.3）；
- 每条消息的 `len` 精确比对 + 结构体逐字段布局，与手册的偏移/缩放**逐项核对无误**
  （NAV-PVT 92 B、EOE 4 B、HPPOSLLH 36 B、HPPOSECEF 28 B、RELPOSNED 64 B、TIMEGPS 16 B）；
- `Fix` 枚举映射遵守"`gnssFixOK` 优先"的有效位原则（§4.1）；
- HP 合成公式与单位换算正确（"何时该用 HP"的判定也已在 04:26 快照中修复，见 §4.5）；
- 无动态分配、无逐字节虚函数（除框架固有的 `read()`），符合飞控要求（§5.5）；
- EOE 缺 PVT 时不推送半截历元、PVT/EOE 的 iTOW 不匹配时丢弃——这两个"宁可丢也不混"的
  决策是对的（§4.2）；
- 固件层已有跨历元重复 iTOW 判重（`navigation_task.cpp:362-367`）、pDOP/hAcc 质量门限、
  降级融合路径，与库内分工合理（§6.4）。

**当前配置（仅 PVT+EOE、10 Hz、921600）下不会触发的风险**

- HP 链路（§4.5）与 RELPOSNED（§4.6）相关路径：因为 `ubx_config.cpp:431-440`
  只启用 NAV-PVT + NAV-EOE，`rel_pos_data_` 恒为 false、HP 消息从不出现，
  这些分支是**死代码**。**一旦启用 RTK/HP（F9P 典型用法）就会立刻暴露**——
  HP 的"何时采用"已修好，但 RELPOSNED 的 iTOW 混帧（P0-3）仍未修，
  属于"明天就会踩"的坑。
- payload 上限（§1.2）与未知消息可观测性（§7.5）：当前只收两条小消息，不会撞上限。

**优先级结论（截至 04:35 复核）**：P0 里只剩 **P0-3（其余 5 条 NAV 消息不校验 iTOW）**。
P0-1（同步回退）、P0-2（HP 粘滞与有效位）、P0-4（时间戳）、P0-5（统计复位）**均已由
并行修改修复**，本文相应章节已改写成"缺陷成因 + 当前实现 + 回归用例"，可直接当验收单。
**P0-3 必须在上 RTK/高精度之前修完**，否则 RELPOSNED 以 1 Hz 输出时 EKF 会拿到过期基线；
其余 P1/P2 项可按 §8 的顺序排。

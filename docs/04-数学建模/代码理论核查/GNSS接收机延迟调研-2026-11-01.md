# GNSS 接收机延迟调研（2026-11-01）

> 目的：给 `BFS_NAVIGATION_GNSS_DELAY_S` 先验、自动延迟估计范围与 PPS 方案提供外部依据，
> 回答“真实接收机延迟到底在什么范围”。

## 1. 延迟的构成

一次 GNSS 观测从“天线收到信号”到“EKF 拿到数据”要经过：

1. **测量 epoch**：接收机基带在整秒附近完成伪距/载波测量（µs 级）；
2. **PVT 解算**：最小二乘/卡尔曼求解位置速度（几 ms 到几十 ms，随卫星数/星座/RTK 状态变化）；
3. **消息打包与串口输出**：UBX-NAV-PVT 约 100 字节，115200 下 8.7 ms、921600 下 1.1 ms；
4. **飞控接收/解析/调度**：UART 中断或轮询 + 帧解析 + 200 Hz 任务排队（通常 <1 ms，最坏一拍 5 ms）。

EKF 的 `measurement_age_s` 应覆盖 1–4；RTK 改正数链路（基站→流动站）属于另一项，见 §4。

## 3. 项目内部实测

来自 `TandemVec-EKF-Report/` 与 `include/ins_gnss_pps_latency.h`：

- **PPS 标定**：真实 50 ms 时，PPS 边沿+PVT 到达中位数估计 **49.4–52.2 ms**（误差约 2 ms）；
- **无 PPS 自动估计**：10,000 例（5–60 m/s、5–120 ms、GNSS 0.3–5 m、三轴 ±0.5 m/s²、20% 3–10 s 失锁）中 99.97% 误差 ≤20 ms，平均绝对 2.54 ms、P95 8.3 ms、最大 22.4 ms；
- **当前默认**：`BFS_NAVIGATION_GNSS_DELAY_S = 0.015f`（15 ms），对低成本单频偏乐观。

## 4. 对固件的建议

1. **默认先验**：15 ms 建议改为 **25–30 ms**（覆盖 M8N 实测 26 ms）；若保留 15 ms，必须依赖自动估计（`BFS_NAVIGATION_GNSS_DELAY_AUTO_ESTIMATE=1`，当前默认已开）。
2. **自动估计范围**：现有 0–100 ms 的 clamp 覆盖主流接收机；>100 ms 更可能是 RTK 链路/失锁异常，不宜继续外推。
3. **PPS 优先**：硬件 PPS 捕获可用时，优先用 PPS 估计（误差 ~2 ms），自动估计作为回退。
4. **RTK 注意**：RTK 改正数链路的差分龄期（50–500 ms）不属于接收机延迟，不应混入 `measurement_age_s`；若融合 RTK 位置，需要单独的 `age_corr` 或使用接收机输出的差分龄期字段。
5. **上板核对**：用 PPS 或 TIMEMARK 实测本机“测量→EKF 入口”的延迟，替换 15/25 ms 先验。

## 5. 结论

真实接收机延迟（测量→消息到达）大致：

- 低成本单频模块：**20–40 ms**（实测 26 ms 含 8 ms 串口）；
- 多频/RTK 模块：**10–30 ms**；
- 测绘级：**<10 ms**；
- 再叠加飞控解析/调度 <5 ms。

因此 15 ms 先验只适合高更新率、低延迟的链路；对常见 M8N 类模块，**25–30 ms 更接近真实**，而 PPS/自动估计应作为最终依据。

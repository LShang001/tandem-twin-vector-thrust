# IMU 采样调度与组合导航消费关系（2026-11-03）

> 对象：ICM-42688-P（SPI1，10 MHz，2 kHz ODR）+ TIM8 6.4 kHz 协作式调度 +
> 15 状态 EKF（200 Hz）。目的：说明“任务执行频率”“芯片采样率”“导航消费”
> 是三件事，并给出实测与优化取舍。

## 1. 调度实现

- TIM8 6.4 kHz 中断只做：`s_timerTicks++`，遍历任务表，按 Q8 误差累积判断到期，
  置 `tasks[i].flag=true`；不在 ISR 里跑任务。
- 主循环 `taskExecutor()` 按注册顺序遍历任务，`flag` 为真就执行；**无抢占、
  无优先级**，一次遍历每个任务最多执行一次。
- IMU 任务注册周期 = `1000 / actualAccelOdrHz()`；42688 为 2 kHz → **3.2 tick**
  （Q8 下 3/4 tick 交替，长期平均 0.5 ms）。`tasks` 表里的“名义 1600 Hz”是
  整数 tick 初值显示，不是平均 2 kHz，也不是芯片 ODR。
- 任务顺序：IMU → DPS310 → Navigation → AnoCom → … → GNC。IMU 排第一，
  但一次 `taskExecutor` pass 只能服务它一次。

## 2. IMU 任务做什么

`handleICM42688()` → `readIMUData()`：

1. `IMU->dataReady()`（读 INT_STATUS 0x2D 的 DATA_RDY_INT）；
2. 有数据才 `getAGT()`：从 0x1D 起一次 14 B SPI burst（温度+加计+陀螺）；
3. 校准/坐标变换/低通/Madgwick；
4. 把**一个样本**的 `ω·dt`、`a·dt` 写入 64 深增量环（`imu_delta_*`），
   同时累加 `acc_sum/gyro_sum`。

没有 FIFO：任务没执行的那一拍，芯片 ODR 已经产生的新样本会被下一拍覆盖，
**这部分样本不会进入 64 深缓冲**。

## 3. 导航怎么消费

`handleNavigationSystem()` 200 Hz（5 ms）：

- `noInterrupts()` 下一次性取走 `imu_sample_count`、`imu_delta_*`、`sum`，
  然后清空缓冲；
- 对每个 delta 做 EKF 时间更新（保留每样本 dt），并用平均加计/陀螺做
  AHRS/静止检测/健康监测；
- 64 深缓冲在 2 kHz 下约 32 ms、1.6 kHz 下约 40 ms；超过则 `imu_delta_overflow`
  置位，导航只看到截断样本。

所以：**导航 200 Hz 是消费者，IMU 2 kHz 是生产者；中间靠 64 深软件缓冲解耦。
缓冲能吸收 5 ms 导航节拍的抖动，但不能补回“IMU 任务没跑而根本没读到的芯片样本”。**

## 4. 实测

| 观测 | 结果 | 说明 |
| --- | --- | --- |
| `health` IMU rate | 1600.0 Hz（静默短窗）/ 1199.5 Hz（83 s 窗口） | 说明存在周期性丢拍，不是固定 2 kHz |
| `tasks` IMU | 名义 1600、实际 1567–1573、avg 104 µs、gap avg 635–651 µs | **DBG 打印本身会加剧丢拍，不能作为飞行速率依据** |
| AnoVars `imu_rate`（非 DBG，15 s） | 平均 **1600.32 Hz**，min 1143.9、max 1763.0 | 非 DBG 遥测流测量，接近名义 2 kHz |
| AnoVars `imu_rate`（非 DBG，60 s） | 平均 **1576.35 Hz**，min 999.6、max 1705.8 | 平均约 98.5%，存在秒级瞬态掉点 |
| Navigation | 200/200 Hz、avg 1450–1500 µs、迟到 0 | 消费端稳定 |
| 64 深缓冲 | 40 ms @1.6 kHz | 导航 5 ms 周期远小于它，正常不溢出 |

## 5. 是否需要匹配/优化

- **任务周期与 ODR 名义匹配**：`1000/ODR` 已按芯片实际值算，不是写死。
- **平均能力接近匹配，但无零丢样保证**：非 DBG 遥测下 15 s 平均 1600.3 Hz、
  60 s 平均 1576.4 Hz；主循环平均 pass ~635–724 µs，Navigation 单次 1.45 ms
  的 pass 会吞掉 2–3 个 IMU 节拍，出现秒级 min≈1 kHz 的瞬态。
- 对 200 Hz 控制环，平均 1.58–1.60 kHz 仍有 ≥7.9 倍余量，静态 EKF 稳定；
  但“任何窗口都 2 kHz 全样本”不成立，瞬态窗口会丢样/混叠。
- **测量口径**：`tasks`/`health` 走 DBG，打印会显著改变结果；核对飞行速率必须用
  非 DBG 的 AnoVars `imu_rate`（`tvc vars watch imu_rate -t 60`）。

### 优化选项（按推荐顺序）

1. **启用 ICM42688 2 KB FIFO，批量读取**（推荐）：任务即使偶尔晚 1–2 ms，
   FIFO 仍保留样本；需扩展 `ImuDevice` 接口、按 FIFO packet 解析，并把
   多样本逐个送入增量缓冲。这是唯一能在不提高主循环频率的前提下保证
   2 kHz 全样本的路径。
2. **专用高优先级采样**（定时器/ISR 读 SPI）：能保证节拍，但 100 µs 级 SPI
   事务放 ISR 风险高，需严格验证中断延迟与总线互斥。
3. **降低 ODR 到 1 kHz**：与现有调度最匹配，但牺牲带宽/延迟，属降级方案。
4. **压缩 Navigation 单次耗时**（float 协方差已做、DTCM 实测无收益）：
   只能缓解，不能从根上保证 2 kHz。

## 6. 结论

- IMU 任务调度是“TIM8 置 flag + 主循环协作执行”，IMU 排第一但仍受整轮 pass
  限制；导航 200 Hz 通过 64 深增量缓冲消费所有已读样本，二者不是硬实时
  生产者/消费者。
- 当前配置（2 kHz ODR、10 MHz SPI、200 Hz EKF）平均采样 1576–1600 Hz，
  非 DBG 下接近名义，静态 EKF 稳定；但存在秒级瞬态掉点，不能承诺任意窗口
  2 kHz 全样本。
- 若应用只要求 200 Hz 控制/导航，当前链路够用，不必立刻改 FIFO；若要
  “零丢样/满 2 kHz”，下一步做 FIFO 批量读取，而不是继续调 SPI 时钟或
  任务周期。

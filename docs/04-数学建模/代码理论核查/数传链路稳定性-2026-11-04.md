# 数传链路稳定性与降载（2026-11-04）

> 链路：飞控 UART5(Serial5) → 空口数传 → PC CH340 接收机（COM9）/ GCS。
> 结论：遥测发送反压会阻塞主循环，导致 P1 IMU ring 积压；降载后 120s 无>100ms gap。

## 1. 基线问题

- `tvc link`：遥测约 654–780 帧/s、坏帧累计 1；参数命令 5/5。
- 120s `tvc record`：行率 59.6Hz，gap p95=24.4ms、p99=30.1ms、max=535.5ms；
  28 次>100ms、2 次>500ms。
- 同时 P1：`imu_rate` 出现 640/6400 异常窗口、`imu_ring_drop` 持续增长，
  60s 复测 std136、drop456。说明不是纯无线丢包，而是发送阻塞主循环。

## 2. 发送负载

`sniff all -t 5` 每5s计数（折算Hz）：

| 帧 | 频率 | 作用 |
|---|---|---|
| 0x01/0x03 | ~96Hz | IMU/姿态 |
| 0x0A | ~96Hz | 目标姿态 |
| 0x21 | ~96Hz | 控制量 |
| 0xF1 | ~96Hz | 执行器输出 |
| 0x40 | ~24Hz | RC |
| 0x30 | ~9.6Hz | GPS |
| 0xF4 | ~9.6Hz（降载后） | IMU健康/采样率 |

## 3. 降载改动

- **0xF4：100Hz→10Hz**。它是诊断帧，不是控制/姿态主链；保留 `imu_rate`/
  `ring_drop` 趋势即可。
- **0x0A/0x21/0xF1：100Hz→50Hz**。这些是GCS显示帧，不是飞控内部闭环输入；
  0x01/0x03 姿态仍100Hz，GPS/RC不变。
- 目的：把空口/接收机反压降到主循环不再被 `Serial6.write` 长时间阻塞。

## 4. 结果

- 120s record：行率 39.8Hz、gap p95=36.2ms、p99=41.6ms、max=47.7ms；
  **0 次>100ms、0 次>500ms**。
- 同段P1：mean=1994.1Hz、std=67.4、min1693/max2231、`ring_drop=0`，验收 PASS。
- 参数连续写148项：**148/148 双确认**（确认帧+读回），rc=0。
- `tvc link` 3次：560–600帧/s、坏帧累计1、参数读/写/写确认全部5/5。

## 5. 验收

```bash
# 链路
tvc --port COM9 link
# 120s记录
tvc --port COM9 record start -o telem.csv -d 120
py -3.12 TandemVec_FCS/tools/verify_telemetry.py telem.csv
# P1
py -3.12 TandemVec_FCS/tools/verify_imu_p1.py telem.csv
```

`verify_telemetry.py` 门限：行率≥35Hz、gap p99≤60ms、max≤100ms且无>100ms、
`imu_ring_drop=0`。

## 6. 边界

- 当前记录行率约40Hz（降载前约60Hz）；若应用必须50Hz显示，需要进一步压缩
  帧长/合并帧/提高空口带宽，不能靠恢复100Hz重建阻塞。
- 本测试只验证**静态链路**；动态/远距离/干扰/天线姿态下的空口丢包仍需实机。
- 发送端已有 `Serial6.availableForWrite()<190` 跳过保护；本次降载进一步减少触发。
- 高频采样测量仍禁止用DBG，数传验收用CSV/`tvc link`。

## 7. 后续加固与边界（2026-11-04）

- AnoCom 组帧所有 flush 点（endGroup、组满、单帧直发）改为 availableForWrite
  检查；不足丢帧并计入 `AnoCom.txDropped()`，不再阻塞主循环。
- MAVLink 所有逐帧写改 `mavWriteNonBlocking`；SYS_STATUS 用真实电池电压；
  新增 GPS_RAW_INT(5Hz)；MAVLink 模式下识别 DBG 转义可切回 AnoCom（无需复位）。
- 调试接口 `health` 新增：`ano_skip/proto_drop/mav_skip/nav_gap_max`、
  `p1 ring_size/ring_drop/isr_empty`、`navprof tu/pos/gnss max`。
- 120s：PASS（gap max40ms、ring_drop0、P1 1977/62.5）。
- 300s：FAIL（gap max258ms、ring_drop9636）；navprof 显示 GNSS 更新偶发
  63.9ms，Nav入口间隔最大274ms。说明 GNSS 延迟更新/重放仍会偶发长时间占用
  主循环，不是串口写阻塞。此问题未解决，不能宣称长期稳定。

## 8. 0xF5链路诊断帧（2026-11-04）

1Hz 帧（32B，8×u32）：`link_seq, link_uptime_ms, ano_skip, ano_proto_drop,
mav_skip, nav_gap_ms, imu_ring_drop, imu_isr_empty`。

用途：区分“板子停/协议丢帧”和“空口/PC丢帧”——板端 seq 连续但GCS缺行是
空口/PC问题；板端 seq 本身停顿或计数增长是固件问题。已上板验证 seq 每秒+1，
字段可写入CSV。

## 9. 300s根因与最终结果（2026-11-04）

根因不是串口组帧，而是 Navigation 尾部每60s一次的多段 `Serial8.print("[EKF]...")`
阻塞打印；它把主循环拖住40ms+，引起ring积压和空口看起来的“长gap”。

处理：默认关闭该诊断打印（`BFS_NAV_EKF_VERBOSE` 未定义）；需要时编译开启，
health/navprof 已能提供同类信息。

关闭后300s：行率42.6Hz、gap p95=31.1ms、p99=35.5ms、max=41.8ms、
>100ms=0、ring_drop=0；同段P1 mean1981.5/std58.3，双脚本PASS。

## 10. 地面待机302ms长停顿与修复（2026-11-04）

- 烧录前68min地面待机：`delay_max_ms=302.8`、`nav_gap=305ms`、ring_drop≈29.8万。
- 根因：1Hz GNSS 延时估计 `TryEstimate()` 在静止时仍进入粗差 InterpRef 循环+
  网格搜索；参考速度噪声/室内GNSS速度噪声都会绕过0.5m/s速度门。
- 修复：静止时直接跳过估计（`is_static_confirmed`）；`TryEstimate`内部先查
  GNSS自报速度，<0.5m/s 立即 NoExcitation，不再跑重计算。
- 烧后120s：gap p99=41.8ms、max=47.6ms、>100ms=0、ring_drop=0；
  P1 mean=2000.3/std=58.8；`delay_max=10.4ms`。

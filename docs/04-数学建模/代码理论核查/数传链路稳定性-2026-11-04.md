# 数传链路稳定性与降载（2026-11-04）

> 链路：飞控 UART5(Serial5) → 空口数传 → PC CH340 接收机（COM9）/ GCS。
> 结论：遥测发送反压会阻塞主循环，导致 P1 IMU ring 积压；降载后 120s 无>100ms gap。

## 1. 基线问题

- `tvc link`：遥测约 654–780 帧/s、坏帧累计 1；参数命令 5/5。
- 120s `tvc record`：行率 59.6Hz，gap p95=24.4ms、p99=30.1ms、max=535.5ms；
  28 次>100ms、2 次>500ms。
- 同时 P1：`imu_rate` 出现 640/6400 异常窗口、`imu_ring_drop` 持续增长，
  60s 复测 std136、drop456。说明不是纯无线丢包，而是发送阻塞主循环。

## 2. 发送负载

`sniff all -t 5` 每5s计数（折算Hz）：

| 帧 | 频率 | 作用 |
|---|---|---|
| 0x01/0x03 | ~96Hz | IMU/姿态 |
| 0x0A | ~96Hz | 目标姿态 |
| 0x21 | ~96Hz | 控制量 |
| 0xF1 | ~96Hz | 执行器输出 |
| 0x40 | ~24Hz | RC |
| 0x30 | ~9.6Hz | GPS |
| 0xF4 | ~9.6Hz（降载后） | IMU健康/采样率 |

## 3. 降载改动

- **0xF4：100Hz→10Hz**。它是诊断帧，不是控制/姿态主链；保留 `imu_rate`/
  `ring_drop` 趋势即可。
- **0x0A/0x21/0xF1：100Hz→50Hz**。这些是GCS显示帧，不是飞控内部闭环输入；
  0x01/0x03 姿态仍100Hz，GPS/RC不变。
- 目的：把空口/接收机反压降到主循环不再被 `Serial6.write` 长时间阻塞。

## 4. 结果

- 120s record：行率 39.8Hz、gap p95=36.2ms、p99=41.6ms、max=47.7ms；
  **0 次>100ms、0 次>500ms**。
- 同段P1：mean=1994.1Hz、std=67.4、min1693/max2231、`ring_drop=0`，验收 PASS。
- 参数连续写148项：**148/148 双确认**（确认帧+读回），rc=0。
- `tvc link` 3次：560–600帧/s、坏帧累计1、参数读/写/写确认全部5/5。

## 5. 验收

```bash
# 链路
tvc --port COM9 link
# 120s记录
tvc --port COM9 record start -o telem.csv -d 120
py -3.12 TandemVec_FCS/tools/verify_telemetry.py telem.csv
# P1
py -3.12 TandemVec_FCS/tools/verify_imu_p1.py telem.csv
```

`verify_telemetry.py` 门限：行率≥35Hz、gap p99≤60ms、max≤100ms且无>100ms、
`imu_ring_drop=0`。

## 6. 边界

- 当前记录行率约40Hz（降载前约60Hz）；若应用必须50Hz显示，需要进一步压缩
  帧长/合并帧/提高空口带宽，不能靠恢复100Hz重建阻塞。
- 本测试只验证**静态链路**；动态/远距离/干扰/天线姿态下的空口丢包仍需实机。
- 发送端已有 `Serial6.availableForWrite()<190` 跳过保护；本次降载进一步减少触发。
- 高频采样测量仍禁止用DBG，数传验收用CSV/`tvc link`。
